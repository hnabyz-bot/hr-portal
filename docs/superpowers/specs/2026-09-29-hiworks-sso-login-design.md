## 1. 무엇이 바뀌나

8월 설계는 "이메일 + 비밀번호로 직접 로그인"이었다. 가비아 회신과 API 문서 확인 결과 **하이웍스 "SSO 외부로 연동"**을 쓸 수 있으므로 로그인을 하이웍스에 맡긴다.

- 직원은 하이웍스에 로그인한 상태에서 **하이웍스 화면의 "인사포털" 메뉴**를 누른다.
- 하이웍스가 **새 탭**으로 포털을 열면서 확인표(token)를 붙여 보낸다. 확인표는 **60초 동안 유효하고 그 안에는 다시 쓸 수 있다**(1회용이 아니다) — 그래서 포털이 한 번 쓴 것을 다시 받지 않는다(§5).
- 포털 서버가 그 확인표를 하이웍스에 되물어 **누구인지(사용자 번호·아이디·이름·사번)** 확인하고 포털 세션을 발급한다.
- **포털은 비밀번호를 받지도, 저장하지도 않는다.**

OAuth(포털 화면에 "하이웍스로 로그인" 버튼)는 문서상 지원 중단이고 가비아도 불가로 회신했다. 그래서 **출입구는 하이웍스 메뉴 하나**다.

## 2. 하이웍스 쪽 사실 (API 문서·가비아 회신)

| 항목 | 내용 |
|---|---|
| 등록 위치 | ① [오피스 관리 > 서비스 연동(API) > SSO 관리 > 외부로 연동]에 연동 URL 등록 — **완료**(2026-10-03, 사이트명 `hr-portal`) ② [기본 정보 > 메뉴 설정 > **바로 가기 메뉴 설정**] → [바로 가기 메뉴 추가]에서 **SSO 연동**을 체크하고 `hr-portal`을 골라 메뉴로 노출 — **등록 완료**(2026-10-12), 지금은 꺼 둠 |
| 연동 URL | `https://hr.abyz-lab.work/api/auth/hiworks` (설정 가이드 1장 E에서 확정) |
| 포털이 받는 요청 | `GET /api/auth/hiworks?token={token}` — 메뉴에 적은 URL(`https://hr.abyz-lab.work/`)이 아니라 **SSO 연동 URL**로, **새 브라우저 탭**으로 온다 (2026-10-12 실측) |
| token | **60초 유효, 60초 안에는 재사용 가능**(1회용이 아니다 — #65 답변 3). 모양은 영문 소문자 a~f와 숫자로 된 **64자리** (2026-10-12 실측) |
| 메뉴 공개 범위 | **전 직원에게 보인다.** 일부 사용자·부서에만 보이게 할 수 없다(#65). 하이웍스 **모바일 앱에는 나오지 않는다** |
| 확인 API | `GET https://link-api.hiworks.com/v4/tokens/{token}` — **인증 헤더 없음, 오피스 토큰 불필요** |
| 응답 | `data.user-no`(고유), `data.user-id`(계정 아이디), `data.user-name`, `data.employee-no`(사번) |
| 응답에 없는 것 | 소속·직급 정보 |

**소속·직급이 오지 않는다.** 그래서 팀장·본부장·HR 같은 **역할은 포털 DB가 정한다.** 하이웍스 값으로 권한을 판단하지 않는다. 소속은 명단 동기화(§11)로 따로 가져온다.

**메뉴는 전 직원에게 보인다.** 하이웍스에서 일부에게만 보이게 할 수 없으므로, 들어와도 되는 사람인지는 포털이 가린다 — 포털 명단에 없는 사람은 막는다(§4 "자동 가입은 없다").

## 3. 로그인 흐름

```
[직원] 하이웍스 로그인 → 오피스 홈의 "인사포털" 메뉴 클릭
   │   하이웍스가 새 탭을 열어 SSO 연동 URL로 보낸다 (메뉴에 적은 URL이 아니다)
   ▼
GET /api/auth/hiworks?token=T
   │
   ├─ ① 형식 검사: T가 a~f·숫자 64자리가 아니면 → 400 안내 화면
   ├─ ② 사용 기록: sha256(T)를 sso_used_tokens에 INSERT. 이미 있으면(키 중복) → 거부 (§5)
   │       하이웍스에 묻기 전에 먼저 기록한다 — 같은 token이 동시에 두 번 와도 하나만 통과한다
   ├─ ③ link-api 조회 (HTTPS, 5초 타임아웃, 리다이렉트 따라가지 않음)
   │       실패·빈 응답 → "하이웍스 확인에 실패했습니다. 메뉴를 다시 눌러주세요"
   ├─ ④ 사용자 찾기 (§4)
   │       못 찾음 → "인사포털에 등록되지 않은 사용자입니다. 인사팀에 문의하세요" (403)
   │       비활성 → 같은 문구 (등록 여부를 구분해 알려주지 않는다)
   │       시범 사용자 명단에 없음(역할 미지정) → "인사포털은 준비 중입니다" 화면 (403)
   ├─ ⑤ 세션 발급 (새 토큰, sessions에 해시 저장), last_login_at 갱신, 감사로그 LOGIN
   └─ ⑥ 302 → "/"  (주소창에서 token을 지운다)
        응답 헤더: Referrer-Policy: no-referrer, Cache-Control: no-store

[요청마다] 쿠키 → 세션 조회 → 만료(마지막 사용 후 4시간 또는 발급 후 12시간)·폐기·사용자 비활성 확인
           → Actor(user_id, role)
```

**②에서 먼저 기록하므로, ③이 실패하면 그 token은 다시 쓸 수 없다.** 메뉴를 다시 누르면 하이웍스가 새 token을 준다(③의 안내 문구 그대로).

**token은 SSO 연동 URL로, 새 탭으로 온다** (2026-10-12 실측). 메뉴에 적은 URL로는 오지 않으므로 받는 곳은 `/api/auth/hiworks` 하나다. 주소창이 있는 일반 탭으로 열리고 하이웍스 화면 안에 끼워 열리지 않는다 — 끼워 열릴 때 생기는 쿠키 차단(로그인이 반복되는 문제)은 해당 없다.

**메뉴는 전 직원에게 보인다** (§2). 그래서 메뉴를 누른 사람은 누구나 ④까지 온다. 포털 명단에 없는 사람과 비활성인 사람은 ④에서 막고, 시범 사용자 명단에 없는 직원에게는 "준비 중" 화면을 보여 준다(§4).

**포털 주소로 바로 들어온 경우** (세션 없음): 화면 전체를 가리고 "하이웍스에서 **인사포털** 메뉴로 들어와 주세요" 안내와 하이웍스 로그인 주소 링크를 보여준다. 정적 페이지(`public/`)는 누구나 받을 수 있지만, **데이터는 전부 `/api/*`에서 세션 검사를 거친다.** 화면을 가리는 것은 안내일 뿐 보안이 아니다(8월 설계 §8 "세 겹").

**1차는 PC 전용이다** (#65 결정 ②). 하이웍스 모바일 앱에는 메뉴가 없어 휴대폰으로는 들어올 길이 없다. 그래서 휴대폰에서 포털 주소를 바로 연 경우(세션 없음)에는 위 안내 대신 "PC의 하이웍스에서 인사포털 메뉴로 열어 주세요"를 보여 준다. 휴대폰인지는 화면 폭(지금 포털이 휴대폰 배치로 바꾸는 기준과 같은 768px 이하)으로 가린다 — 어느 안내를 보여 줄지 고르는 용도일 뿐 차단 장치가 아니다. 휴대폰에서 로그인해 쓰는 방법(QR 등록)은 §13 "추후"로 분리한다.

**로그아웃**은 포털 세션만 폐기한다. 하이웍스는 로그인 상태로 남으므로 메뉴를 다시 누르면 바로 들어온다. 공용 PC에서는 하이웍스도 로그아웃해야 한다고 로그아웃 화면에 적는다.

## 4. 사람 연결 규칙

```
1. users.hiworks_user_no = data.user-no 인 행 → 그 사람
2. 없으면 → 미등록
```

`hiworks_user_no`는 로그인 때 채우지 않는다. **명단 동기화(§11)가 미리 채워 둔다.**

- **`user-no`로 찾는 이유**: 사번은 오타·변경이 있을 수 있지만 `user-no`는 하이웍스가 계정마다 붙이는 고유 번호다.
- **사번으로 맞추는 첫 로그인 연결 단계가 필요 없어진다 — 단, 조건이 있다.** 조직 조회가 주는 구성원 번호(`user_no`)가 SSO 응답의 `user-no`와 같은 번호여야 한다. 2026-10-03 실측으로는 같은 번호 체계로 보이지만 **추정**이다. **같은지는 첫 실연결 때 확인한다**(§7 3단계).
- **자동 가입은 없다 — 유지.** 메뉴가 전 직원에게 보이므로(§2) 이 규칙이 들어올 사람을 가리는 문이다. 명단 동기화가 직원을 `users`에 올려도 **HR이 역할을 지정하기 전에는 들어올 수 없다**(§6). 역할을 모르는 사람을 들이지 않는다.
- **시범 사용자 명단** (#65 결정 ①): 메뉴를 켜면 전 직원에게 보이므로, 시범 운영 동안에는 명단에 있는 사람만 들인다. **명단 = HR이 역할을 지정한 사람**이다 — 표를 따로 만들지 않는다. 직원 표에는 있지만 역할이 없는 사람은 "인사포털은 준비 중입니다" 화면을 본다. 명단은 HR이 역할 지정 화면에서 관리하고, 전 직원에게 열 때는 남은 직원에게 역할을 지정한다. 역할은 미리 정해 두고 출입만 막아야 하는 일이 생기면 그때 출입 허용 칸을 따로 둔다.
- **비활성화**: HR이 포털에서 사용자를 비활성화하면 그 사람의 세션을 **즉시 전부 폐기**한다. 하이웍스 계정 정지만으로는 이미 발급된 포털 세션(4시간, 활동하면 연장, 최대 12시간)이 끊기지 않으므로, 퇴사 처리 순서에 "포털 비활성화"를 넣는다. 명단 동기화가 하이웍스에서 사라진 사람을 비활성으로 표시할 때도 같은 규칙으로 세션을 폐기한다. 다만 동기화는 하루 1회라 **퇴사 당일에는 HR이 직접 비활성화한다.**

### 번호 체계가 다를 때의 대안 — 사번으로 첫 연결 (9/29 설계)

첫 실연결에서 두 번호가 다르면 `hiworks_user_no`를 미리 채울 수 없다. 그때는 위 2번 앞에 아래를 넣는다.

```
(대안) users.employee_no = data.employee-no 이고 users.name = data.user-name 이고
       hiworks_user_no IS NULL 인 행
       → 그 사람. 이때 hiworks_user_no를 저장하고 감사로그 SSO_LINK를 남긴다 (첫 로그인 연결)
```

- **이름도 같아야 연결한다.** 하이웍스의 사번은 하이웍스 관리 권한이 있으면 바꿀 수 있다. 사번만 보면, 아직 로그인한 적 없는 사람(예: HR·본부장)의 사번을 자기 계정에 넣고 들어와 그 사람으로 **영구 연결**될 수 있다(#51 검토 10/1 ②).
- **연결이 일어나면 감사로그 `SSO_LINK`에 남기고 HR 화면에 보여 준다.** 잘못된 연결을 HR이 알아채고 끊을 수 있어야 한다.
- `users.employee_no`는 **중복 금지(UNIQUE)**다. 지금 스키마에 이미 있고 그대로 둔다(§6).
- `hiworks_user_no IS NULL` 조건을 두는 이유: 이미 다른 하이웍스 계정과 연결된 사람을 사번만 같다고 가로채지 못하게 한다.
- 사번이 비어 있는 하이웍스 계정은 이 연결이 실패하므로 미등록으로 처리된다. HR이 하이웍스에 사번을 넣어야 한다.
- 권한이 큰 사람의 첫 연결을 HR이 승인하게 할지는 §10에서 정한다.

이 연결 규칙은 순수 함수 `resolve_sso_user(token_data, users) -> 결과`로 만들어 DB 없이 selfcheck에서 검증한다.

## 5. 보안 설계

| 위협 | 대응 |
|---|---|
| **token이 로그에 남는다** — nginx 기본 로그는 주소 전체(`?token=`)를 기록한다 | `/api/auth/hiworks` 위치만 **쿼리 없이 기록**하는 로그 형식을 쓴다. Flask 쪽 로그에도 token을 찍지 않는다 |
| **token이 다른 사이트로 샌다** (Referer) | 수신 즉시 302로 token 없는 주소로 보내고, `Referrer-Policy: no-referrer` |
| **token 재사용** — 하이웍스 token은 60초 유효이고 그 안에는 **다시 쓸 수 있다**(#65 답변 3) | 사용한 token의 해시를 `sso_used_tokens`에 **60초** 보관하고 재사용을 거부한다(#65 결정 ③ — token 유효시간과 같게). **하이웍스에 묻기 전에 먼저 기록한다**(§3 ②) — `token_hash`가 기본 키라, 같은 token이 거의 동시에 두 번 와도 DB가 하나만 받아 준다. 하이웍스가 막아 주지 않으므로 포털의 재사용 거부가 **꼭 필요하다** |
| 가짜 확인 서버 | 확인 주소는 코드에 고정(`link-api.hiworks.com`), HTTPS 인증서 검증, 리다이렉트 불허 |
| 수신 경로 두드리기 (무작위 token 대입) | **실제 접속자 주소(`CF-Connecting-IP` 헤더)**당 1분 30회 초과 시 429. 포털은 Cloudflare를 거쳐 들어오므로 서버가 보는 접속 주소는 전 직원이 같다 — 그 주소로 세면 여러 명이 동시에 메뉴를 누를 때 전원이 막힌다. 서버는 밖에서 Cloudflare로만 들어올 수 있어 이 헤더를 믿을 수 있다. token은 하이웍스가 발급하므로 대입 성공 가능성은 낮지만, 포털이 link-api를 과도하게 호출하지 않게 막는다 |
| 세션 고정 | 로그인마다 새 세션 토큰을 만든다. 로그인 전 쿠키 값을 이어 쓰지 않는다 |
| CSRF | 쿠키 `SameSite=Lax` + 상태를 바꾸는 API는 POST 전용 + `Origin` 헤더가 포털 주소인지 검사 |
| 역할 위조 | 역할은 포털 DB에서만 읽는다. 하이웍스 응답·화면 값으로 판단하지 않는다 |

**오피스 토큰은 로그인에 필요 없다.** link-api 조회에는 인증 헤더가 없다. 오피스 토큰은 알림·전자결재·**명단 동기화(§11)**에서만 쓴다. 그래서 **로그인 경로는 오피스 토큰 없이 PC에서 만들고 시험할 수 있다** (설정 가이드 3장과 같은 결론). 오피스 토큰이 필요한 것은 명단 동기화의 실제 호출뿐이고, 그 시험은 포털 서버에서 한다(§8).

### 겸직 C — 구조는 열어 두고 운영은 막는다 (#32 4번, 2026-10-12 확정)

8월 설계는 `users.role` 한 칸, 곧 "한 사람 = 역할 하나"였다(8월 설계 §4 가정). 인사담당자가 **C(지금은 없지만 앞으로 생길 수 있다)**로 정했다. 직원 정보는 로그인 구현 때 처음 저장되므로 지금 바꾸면 옮길 자료가 없다.

|---|---|

## 7. 개발·검증 방법 (시험용 하이웍스가 없다)

가비아는 시험용 오피스를 제공하지 않는다. 그래서 단계를 나눈다.

| 단계 | 방법 | 실제 하이웍스 |
|---|---|---|
| 1. 로직 | `resolve_sso_user`, token 형식 검사, 재사용 검사를 selfcheck로 검증 | 불필요 |
| 2. 경로 | 서버 설정 `HIWORKS_LINK_API_BASE`로 확인 주소를 **로컬 가짜 서버**로 바꿔 전체 흐름을 시험. 운영에서는 이 값을 두지 않아 기본값(`https://link-api.hiworks.com`)만 쓴다 | 불필요 |
| 3. 실연결 | **확인 완료 (2026-10-12, 메뉴를 잠깐 켜서 확인)**: token이 SSO 연동 URL로 온다 · 새 브라우저 탭으로 열린다 · token은 a~f·숫자 64자리. 유효시간 60초·재사용 가능은 #65 답변으로 확인. **남은 확인**: ① token 조회(link-api) 응답 ② 조직 조회의 `user_no`와 SSO `user-no`가 같은 번호 체계인지(§4). 포털 수신 경로를 만든 뒤 **시험용 계정 1개**로 확인한다 | 필요 |
| 4. 공개 | 메뉴는 **등록 완료·꺼 둠**(2026-10-12). "로그인 준비 완료" 통보 → 하이웍스 API 담당자가 메뉴 스위치를 켠다. 하이웍스 **모바일 앱에는 메뉴가 나오지 않는다**(#65) — 확인할 것이 아니라 확정된 사실이다 | 필요 |

`HIWORKS_LINK_API_BASE`는 개발용 우회로다. 운영 서버에 실수로 들어가면 본인 확인이 가짜 서버로 넘어가 **누구든 아무나로 로그인**할 수 있게 된다. 그래서 **운영 모드에서 이 값이 있으면 경고가 아니라 서버 시작을 거부한다.** 운영 모드 표시는 `.env`가 아니라 `docker-compose.yml`에 고정해 둔다 — 서버는 항상 이 파일로 뜨므로 빠뜨릴 수 없다(PC에서의 개발·시험은 이 파일 없이 실행한다). 변수 이름은 구현 PR(§8 4단계)에서 확정한다.

## 9. 개발본부장 검토 요청 항목

8월 설계 §11의 여섯 가지를 아래로 바꾼다.

1. **token 취급** — 로그(nginx·Flask)에 남지 않는가, 302로 주소에서 지워지는가, `Referrer-Policy`가 붙는가
2. **token 재사용 거부** — 하이웍스에 묻기 전에 먼저 기록하는가, 같은 token이 동시에 두 번 와도 하나만 통과하는가
3. **확인 서버 고정** — link-api 주소가 코드 고정·HTTPS 검증·리다이렉트 불허인가, 운영 모드에 `HIWORKS_LINK_API_BASE`가 있으면 서버가 시작을 거부하는가
4. **사람 연결 규칙** — 이미 연결된 사람을 사번으로 가로챌 수 없는가, 미등록·비활성 안내가 같은 문구인가, (사번 연결 대안을 쓸 때) 이름까지 같아야 연결되고 `SSO_LINK`로 남는가
5. **세션** — 쿠키 세 플래그, 토큰 해시 저장, 비활성화 시 즉시 폐기, **로그인마다 새 세션 발급**(로그인 전 쿠키 값을 이어 쓰지 않는다), 최대 상한(발급 후 12시간)
6. **`PRAGMA foreign_keys = ON`** — 연결 직후 가장 먼저 켜지는가 (#35 정정 ②)
7. **백업** — 8월 설계 §9 + #36 항목 7·8
8. **겸직 구조·시범 사용자 명단** — `user_roles`에 역할을 여러 개 담을 수 있는가, 지금은 두 번째 역할이 거부되는가, 역할이 없는 사람(시범 사용자 명단 밖)이 세션을 받지 못하고 "준비 중" 화면을 보는가 (§4·§6)
9. **명단 동기화** — 조회 실패·빈 응답일 때 아무도 비활성화되지 않는가, 비활성인 사람을 다시 켜지 않는가, 역할을 건드리지 않는가 (§11)
10. **전자서명 기록 파기** — 서명 완료 계약의 수정 금지 장치를 유지하면서 기한이 지난 서명 그림·접속 IP만 지울 수 있는가, 감사 로그에 남은 접속 IP는 어떻게 할 것인가 (§12)
11. **요청 빈도 제한** — `CF-Connecting-IP` 기준으로 세는가, 여러 직원이 동시에 메뉴를 눌러도 서로 막히지 않는가 (§5)
12. **다른 사이트에서 몰래 보내는 요청 막기(CSRF)** — 상태를 바꾸는 API가 POST 전용이고 `Origin` 헤더를 검사하는가 (§5)

## 11. 직원 명단 동기화 (2026-10-12 추가)

하이웍스에서 직원 명단·조직을 가져올 수 있다(2026-10-03 실측, 설정 가이드 5장 "조직도"). HR이 직원을 포털에 하나하나 입력하지 않고 **서버가 하루 1회 가져온다.** 흐름 그림은 설정 가이드 5장 "그림으로 보기" ④.

| 항목 | 내용 |
|---|---|
| 언제 | 서버가 **하루 1회** (하이웍스 호출 한도는 회사당 하루 1,000건 — 동기화는 한 번에 2건) |
| 부르는 것 | `GET /hrm/v2/users`, `GET /hrm/v2/organizations` — 오피스 토큰과 **`Content-Type: application/json` 필수**(GET도). 빠지면 HTTP 202에 `code: ERR`가 온다. HTTP 상태가 아니라 응답의 `code`로 성공을 판단한다 |
| 받는 것 | 사용자 번호, 아이디, 이름, 메일, 전화, 소속 조직. **직급·직책·사번·입사일은 오지 않는다** |
| 비교 기준 | **하이웍스 사용자 번호** (`users.hiworks_user_no`) |
| 새 사람 | `users`에 추가한다. **역할은 비워 둔다** — HR이 역할을 지정해야 들어올 수 있다(§4) |
| 고치는 것 | **본부·팀 구성, 소속, 연락처(메일·전화)** — 이것만 하이웍스 값으로 고친다 |
| 부서가 없는 계정 | 올리지 않는다 (§10) |
| 명단에서 사라진 사람 | 비활성으로 표시하고 세션을 폐기한다(§4) |
| 손대지 않는 것 | **역할**(직원·팀장·본부장·HR)과 **조직장 지정** — HR이 포털에서 지정한다. **비활성인 사람** — 동기화가 다시 켜지 않는다. 다시 켜는 것은 HR만 한다 |
| 실패했을 때 | 조회 실패, `code`가 성공이 아님, 받은 명단이 비어 있음 → **아무것도 바꾸지 않고** 기록만 남긴다. 하이웍스 쪽 문제로 전 직원이 비활성화되는 일을 막는다 |

- **하이웍스가 먼저 알려 주는 기능은 확인되지 않았다.** 그래서 포털이 하루 1회 물어본다. 입사·이동은 다음 동기화 때 반영되고, 퇴사는 기다리지 않고 HR이 당일에 비활성화한다(§4).
- 조직 조회의 사용자 번호가 SSO의 `user-no`와 같은 번호 체계인지는 첫 실연결 때 확인한다(§7 3단계). 다르면 §4의 대안을 쓴다.
- 지금 스키마의 `users.employee_no`·`hire_date`는 비울 수 없는 칸인데 하이웍스 조직 조회에는 둘 다 없다. 동기화로 들어온 행을 위해 **비울 수 있게 바꾼다**(`employee_no`의 중복 금지는 유지). 채우는 방법은 §10.
- 본부·팀도 하이웍스 조직을 따라 고친다. 그러려면 하이웍스 조직과 포털 부서(`departments`)를 짝지어 두어야 한다. 하이웍스 조직은 21개(회사 1 + 20개, 2단계)로 포털 조직도(본부 6·팀 14)와 개수가 같다. 짝짓는 칼럼과 이름 대응은 구현 PR(§8 3단계)에서 확정한다.
- 비교 규칙(추가·소속 변경·비활성 목록 만들기)은 `resolve_sso_user`처럼 순수 함수로 만들어 DB·하이웍스 없이 selfcheck에서 검증한다. 오피스 토큰이 필요한 실제 호출 시험은 포털 서버에서 하고(§8), 토큰 값과 직원 정보 값은 출력하지 않는다.

## 12. 전자서명 기록 보관 (2026-10-12 추가, #32 6번 확정)

연봉계약서에 서명할 때 서명 그림과 접속 IP를 함께 남긴다. 둘 다 개인정보라 보관 기한을 둔다. [평가·계약 설계](2026-08-24-hr-evaluation-contract-design.md)는 "무기한 보관, 보관기간이 정해지면 파기 절차를 추가한다"였다.

| 항목 | 내용 |
|---|---|
| 보관 기한 | **계약 종료 후 3년** (`salary_contracts.contract_ends_on` 기준) |
| 기한이 지나면 지우는 것 | **서명 그림**(`signature_image`)과 **접속 IP**(`signer_ip`) — 이 둘만 |
| 남기는 것 | 계약서(본문·금액·기간)와 **"누가 언제 서명했다"** 기록(`signer_user_id`·`signer_name`·`signed_at`), 문서 해시(`document_hash`) |

구현할 때 풀어야 할 것 — 지금 스키마는 "서명 완료된 계약은 고칠 수 없다"로 잠겨 있다.

- `contract_signed_chk`는 서명 완료 계약에 서명 그림·접속 IP가 **반드시 있어야** 한다고 검사한다 → 파기한 날짜 칸을 두고, 그 칸이 채워진 계약은 두 값이 비어 있어도 되게 바꾼다.
- `trg_contract_lock_frozen`은 서명 완료 계약의 계약 내용·서명 기록 칸을 고치지 못하게 막는다 → **기한이 지난 계약에서 이 두 값을 비우는 것 하나만** 허용한다. 그 밖의 수정은 지금처럼 막는다.
- 파기하면 감사 로그에 남긴다(어느 계약에서 언제 지웠는지. 지운 값은 남기지 않는다).
- 감사 로그(`audit_logs.ip`)에도 서명 때의 접속 IP가 남을 수 있는데, 감사 로그는 수정·삭제가 막혀 있다. 같은 기한으로 지울지는 개발본부장 검토 항목이다(§9).
- 계약서 PDF에 서명 그림이 찍힌다면 PDF도 같은 기한의 대상이다. PDF 생성은 아직 구현 전이므로 만들 때 이 기한을 반영한다.

구현 시점은 로그인과 별개다. **연봉계약서를 실제로 저장하기 전**에 넣는다(#32).

### 13.1 추후 — 휴대폰에서 쓰기 (QR 등록)

1차는 PC 전용이다(#65 결정 ②, 본부장 의견 "PC에서 먼저 구현하고 휴대폰은 추후"). 휴대폰 단계에서는 인사담당자가 정한 아래 방식(#65, 2026-10-02 확정)을 그대로 쓴다.

| 항목 | 내용 |
|---|---|
| 등록 | PC에서 SSO로 로그인한 상태로 "휴대폰 등록" → QR 표시(**3분 유효, 1회용**) → 휴대폰 카메라로 찍으면 그 휴대폰이 등록된다 |
| 그 뒤 | 휴대폰 홈 화면 바로가기를 누르면 바로 포털이 열린다 (비밀번호 없음) |
| 유지 기간 | 마지막으로 쓴 날부터 **30일**, 쓸 때마다 연장 |
| 해제 | 본인이 등록된 휴대폰 목록에서 해제(분실 시), HR이 해제. 포털 사용자가 비활성화되면 휴대폰도 함께 막힌다 |
| 급여·계약 | 휴대폰에서도 열린다. 금액은 가린 상태로 시작한다 |

설계에 더해질 것: QR용 1회용 표, 기기별 세션(기기 이름·등록일·마지막 사용일), 기기 세션 폐기. PC 세션(4시간, 최대 12시간)과 유지 기간이 달라 세션을 두 종류로 다뤄야 한다. 휴대폰 단계를 시작할 때 이 문서를 다시 개정한다.
