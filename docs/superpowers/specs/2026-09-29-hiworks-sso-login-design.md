## 1. 무엇이 바뀌나

8월 설계는 "이메일 + 비밀번호로 직접 로그인"이었다. 가비아 회신과 API 문서 확인 결과 **하이웍스 "SSO 외부로 연동"**을 쓸 수 있으므로 로그인을 하이웍스에 맡긴다.

- 직원은 하이웍스에 로그인한 상태에서 **하이웍스 화면의 "인사포털" 메뉴**를 누른다.
- 하이웍스가 **새 탭**으로 포털을 열면서 확인표(token)를 붙여 보낸다. 확인표는 **60초 동안 유효하고 그 안에는 다시 쓸 수 있다**(1회용이 아니다) — 그래서 포털이 한 번 쓴 것을 다시 받지 않는다(§5).
- 포털 서버가 그 확인표를 하이웍스에 되물어 **누구인지(사용자 번호·아이디·이름·사번)** 확인하고 포털 세션을 발급한다.
- **포털은 비밀번호를 받지도, 저장하지도 않는다.**

OAuth(포털 화면에 "하이웍스로 로그인" 버튼)는 문서상 지원 중단이고 가비아도 불가로 회신했다. 그래서 **출입구는 하이웍스 메뉴 하나**다.

| 메뉴 공개 범위 | **전 직원에게 보인다.** 일부 사용자·부서에만 보이게 할 수 없다(#65). 하이웍스 **모바일 앱에는 나오지 않는다** |
| 확인 API | `GET https://link-api.hiworks.com/v4/tokens/{token}` — **인증 헤더 없음, 오피스 토큰 불필요** |
| 응답 | `data.user-no`(고유), `data.user-id`(계정 아이디), `data.user-name`, `data.employee-no`(사번) |
| 응답에 없는 것 | 소속·직급 정보 |

**소속·직급이 오지 않는다.** 그래서 직책(팀장·본부장·대표이사)과 HR 권한은 **포털 DB가 정한다**(§6 "사람별 설정"). 하이웍스 값으로 권한을 판단하지 않는다. 소속은 명단 동기화(§11)로 따로 가져온다.

**메뉴는 전 직원에게 보인다.** 하이웍스에서 일부에게만 보이게 할 수 없으므로, 들어와도 되는 사람인지는 포털이 가린다 — 포털 명단에 없는 사람은 막는다(§4 "자동 가입은 없다").

## 3. 로그인 흐름

```
[직원] 하이웍스 로그인 → 오피스 홈의 "인사포털" 메뉴 클릭
   │   하이웍스가 새 탭을 열어 SSO 연동 URL로 보낸다 (메뉴에 적은 URL이 아니다)
   ▼
GET /api/auth/hiworks?token=T
   │
   ├─ ① 형식 검사: T가 a~f·숫자 64자리가 아니면 → 400 안내 화면
   ├─ ② 사용 기록: sha256(T)를 sso_used_tokens에 INSERT. 이미 있으면(키 중복) → 거부 (§5)
   │       하이웍스에 묻기 전에 먼저 기록한다 — 같은 token이 동시에 두 번 와도 하나만 통과한다
   ├─ ③ link-api 조회 (HTTPS, 5초 타임아웃, 리다이렉트 따라가지 않음)
   │       실패·빈 응답 → "하이웍스 확인에 실패했습니다. 메뉴를 다시 눌러주세요"
   ├─ ④ 사용자 찾기 (§4)
   │       못 찾음 → "인사포털에 등록되지 않은 사용자입니다. 인사팀에 문의하세요" (403)
   │       비활성 → 같은 문구 (등록 여부를 구분해 알려주지 않는다)
   │       HR이 한 명도 없고 서버 설정의 첫 HR 번호와 같은 사람 → HR로 지정하고 계속 (§4 "첫 HR 담당자")
   │       시범 사용자 명단에 없음(포털 사용 꺼짐) → "인사포털은 준비 중입니다" 화면 (403)
   ├─ ⑤ 세션 발급 (새 토큰, sessions에 해시 저장), last_login_at 갱신, 감사로그 LOGIN
   └─ ⑥ 302 → "/"  (주소창에서 token을 지운다)
        응답 헤더: Referrer-Policy: no-referrer, Cache-Control: no-store
        쿠키: hr_session(브라우저를 끄면 사라짐) + hr_entry=1(1분, 화면이 "하이웍스로 연 창" 표시를 남기고 지움 — 2026-10-19)

[요청마다] 쿠키 → 세션 조회 → 만료(마지막 사용 후 4시간 또는 발급 후 12시간)·폐기·사용자 비활성 확인
           → Actor(user_id, 직책, HR 권한)   -- §6 "사람별 설정"
```

**②에서 먼저 기록하므로, ③이 실패하면 그 token은 다시 쓸 수 없다.** 메뉴를 다시 누르면 하이웍스가 새 token을 준다(③의 안내 문구 그대로).

**token은 SSO 연동 URL로, 새 탭으로 온다** (2026-10-12 실측). 메뉴에 적은 URL로는 오지 않으므로 받는 곳은 `/api/auth/hiworks` 하나다. 주소창이 있는 일반 탭으로 열리고 하이웍스 화면 안에 끼워 열리지 않는다 — 끼워 열릴 때 생기는 쿠키 차단(로그인이 반복되는 문제)은 해당 없다.

**메뉴는 전 직원에게 보인다** (§2). 그래서 메뉴를 누른 사람은 누구나 ④까지 온다. 포털 명단에 없는 사람과 비활성인 사람은 ④에서 막고, 시범 사용자 명단에 없는 직원에게는 "준비 중" 화면을 보여 준다(§4).

**포털 주소로 바로 들어온 경우** (세션 없음): 화면 전체를 가리고 "하이웍스에서 **인사포털** 메뉴로 들어와 주세요" 안내와 하이웍스 로그인 주소 링크를 보여준다. 정적 페이지(`public/`)는 누구나 받을 수 있지만, **데이터는 전부 `/api/*`에서 세션 검사를 거친다.** 화면을 가리는 것은 안내일 뿐 보안이 아니다(8월 설계 §8 "세 겹").

**세션이 남아 있어도 주소로 연 창** (2026-10-19): PC는 하이웍스 메뉴로 연 창에서만 쓴다. 주소를 직접 쳐서 연 창에는 ⑥의 표시가 없으므로 화면이 로그아웃(`POST /api/auth/logout`)하고 위와 같은 안내를 띄운다. 새로 고침은 그대로다.

**이미 있는 API도 세션 검사를 거친다.** 규정 검색(`/api/rules`, `/api/rules/search`, `/api/rules/faq`, `/api/rules/<id>`, `/api/rules/<id>/file`)과 경비 산출기(`/api/calculate`, `/api/search-places`, `/api/export/*`, `/api/voucher`)도 세션이 없으면 401이다. 세션 없이 열어 두는 것은 로그인 받는 곳(`/api/auth/hiworks`)과 `/api/health`뿐이다. 새로 만드는 API도 같다.

**1차는 PC 전용이다** (#65 결정 ②). 하이웍스 모바일 앱에는 메뉴가 없어 휴대폰으로는 들어올 길이 없다. 그래서 휴대폰에서 포털 주소를 바로 연 경우(세션 없음)에는 위 안내 대신 "PC의 하이웍스에서 인사포털 메뉴로 열어 주세요"를 보여 준다. 휴대폰인지는 화면 폭(지금 포털이 휴대폰 배치로 바꾸는 기준과 같은 768px 이하)으로 가린다 — 어느 안내를 보여 줄지 고르는 용도일 뿐 차단 장치가 아니다. 휴대폰에서 로그인해 쓰는 방법(QR 등록)은 §13 "추후"로 분리한다.

**로그아웃**은 포털 세션만 폐기한다. 하이웍스는 로그인 상태로 남으므로 메뉴를 다시 누르면 바로 들어온다. 공용 PC에서는 하이웍스도 로그아웃해야 한다고 로그아웃 화면에 적는다.

## 4. 사람 연결 규칙

```
1. users.hiworks_user_no = data.user-no 인 행 → 그 사람
2. 없으면 → 미등록
```

`hiworks_user_no`는 로그인 때 채우지 않는다. **명단 동기화(§11)가 미리 채워 둔다.**

- **`user-no`로 찾는 이유**: 사번은 오타·변경이 있을 수 있지만 `user-no`는 하이웍스가 계정마다 붙이는 고유 번호다.
- **사번으로 맞추는 첫 로그인 연결 단계가 필요 없어진다 — 단, 조건이 있다.** 조직 조회가 주는 구성원 번호(`user_no`)가 SSO 응답의 `user-no`와 같은 번호여야 한다. 2026-10-03 실측으로는 같은 번호 체계로 보이지만 **추정**이다. **같은지는 첫 실연결 때 확인한다**(§7 3단계).
- **자동 가입은 없다 — 유지.** 메뉴가 전 직원에게 보이므로(§2) 이 규칙이 들어올 사람을 가리는 문이다. 명단 동기화가 직원을 `users`에 올려도 **HR이 포털 사용을 켜기 전에는 들어올 수 없다**(§6 "사람별 설정"). HR이 확인하지 않은 사람을 들이지 않는다.
- **시범 사용자 명단** (#65 결정 ①): 메뉴를 켜면 전 직원에게 보이므로, 시범 운영 동안에는 명단에 있는 사람만 들인다. **명단 = 포털 사용이 켜진 사람**이다 — 표를 따로 만들지 않고 `users`에 칸 하나를 둔다(§6). 꺼져 있는 사람은 "인사포털은 준비 중입니다" 화면을 본다. 명단은 HR이 구성원 설정 화면에서 관리하고, 전 직원에게 열 때는 남은 직원의 포털 사용을 켠다. (처음에는 "역할을 지정한 사람"으로 했으나, 직책이 없는 일반 직원과 아직 정하지 않은 사람을 구분할 수 없어 2026-10-12에 출입 칸을 따로 두었다.)
- **비활성화**: HR이 포털에서 사용자를 비활성화하면 그 사람의 세션을 **즉시 전부 폐기**한다. 하이웍스 계정 정지만으로는 이미 발급된 포털 세션(4시간, 활동하면 연장, 최대 12시간)이 끊기지 않으므로, 퇴사 처리 순서에 "포털 비활성화"를 넣는다. 명단 동기화가 하이웍스에서 사라진 사람을 비활성으로 표시할 때도 같은 규칙으로 세션을 폐기한다. 다만 동기화는 하루 1회라 **퇴사 당일에는 HR이 직접 비활성화한다.**

### 번호 체계가 다를 때의 대안 — 사번으로 첫 연결 (9/29 설계)

첫 실연결에서 두 번호가 다르면 `hiworks_user_no`를 미리 채울 수 없다. 그때는 위 2번 앞에 아래를 넣는다.

```
(대안) users.employee_no = data.employee-no 이고 users.name = data.user-name 이고
       hiworks_user_no IS NULL 인 행
       → 그 사람. 이때 hiworks_user_no를 저장하고 감사로그 SSO_LINK를 남긴다 (첫 로그인 연결)
```

- **이름도 같아야 연결한다.** 하이웍스의 사번은 하이웍스 관리 권한이 있으면 바꿀 수 있다. 사번만 보면, 아직 로그인한 적 없는 사람(예: HR·본부장)의 사번을 자기 계정에 넣고 들어와 그 사람으로 **영구 연결**될 수 있다(#51 검토 10/1 ②).
- **연결이 일어나면 감사로그 `SSO_LINK`에 남기고 HR 화면에 보여 준다.** 잘못된 연결을 HR이 알아채고 끊을 수 있어야 한다.
- `users.employee_no`는 **중복 금지(UNIQUE)**다. 지금 스키마에 이미 있고 그대로 둔다(§6).
- `hiworks_user_no IS NULL` 조건을 두는 이유: 이미 다른 하이웍스 계정과 연결된 사람을 사번만 같다고 가로채지 못하게 한다.
- 사번이 비어 있는 하이웍스 계정은 이 연결이 실패하므로 미등록으로 처리된다. HR이 하이웍스에 사번을 넣어야 한다.
- 권한이 큰 사람의 첫 연결을 HR이 승인하게 할지는 §10에서 정한다.

이 연결 규칙은 순수 함수 `resolve_sso_user(token_data, users) -> 결과`로 만들어 DB 없이 selfcheck에서 검증한다.

### 첫 HR 담당자 — 서버 설정으로 지정 (2026-10-12 추가, 인사담당자 확정)

포털 사용과 HR 권한은 HR이 화면에서 정한다(§6 "사람별 설정"). 그런데 처음에는 HR 권한이 있는 사람도, 포털 사용이 켜진 사람도 없어 **아무도 들어올 수 없다.** 그래서 첫 HR 한 명만 화면 밖에서 정한다.

```
§3 ④에서 사람을 찾은 뒤, 아래가 모두 참이면 그 사람의 HR 권한과 포털 사용을 켜고 로그인을 이어 간다
  - 활성 사용자 중 HR(HR 권한이 있고 포털 사용이 켜진 사람)이 한 명도 없다
  - 서버 설정값(첫 HR의 하이웍스 사용자 번호)이 비어 있지 않고, 그 사람의 hiworks_user_no와 같다
```

| 항목 | 내용 |
|---|---|
| 적는 곳 | 서버 `.env` — 오피스 토큰과 같은 자리다. 변수 이름 **`HIWORKS_FIRST_HR_USER_NO`** (4단계에서 확정) |
| 적는 값 | 첫 HR의 **하이웍스 사용자 번호** 한 개. 아이디·메일·사번으로 맞추지 않는다 — 하이웍스 관리 권한이 있으면 바꿀 수 있는 값이다(위 대안에서 이름까지 보는 것과 같은 이유). 번호는 명단 동기화(§11)가 채운 `users`에서 서버 담당자가 찾는다 |
| 첫 대상 | **인사담당자 한 명** (확정). 다른 HR은 그 사람이 구성원 설정 화면에서 지정한다 |
| 작동하는 때 | **활성 HR이 0명일 때만.** HR이 한 명이라도 있으면 설정값을 보지 않는다 — 설정에 남아 있는 번호로 다시 HR이 되는 일은 없다 |
| 직책이 있던 사람 | 직책은 그대로 두고 HR 권한만 켠다 — HR 권한은 직책과 따로다(§6). HR이 모두 빠진 뒤 설정값을 다른 사람으로 고쳐 다시 여는 경우다 |
| 기록 | `user_roles.granted_by`는 비우고(사람이 아니라 시스템), 감사로그 `HR_BOOTSTRAP`을 남겨 HR 화면에 보여 준다 |
| 마지막 HR 보호 | 활성 HR이 한 명뿐이면 화면에서 그 사람의 HR 권한·포털 사용을 끌 수 없고 비활성화할 수도 없다. 다른 HR을 먼저 지정해야 한다. 명단 동기화의 비활성 표시(§11)는 막지 않는다 — 그렇게 0명이 되면 위 규칙이 다시 작동한다 |
| 값이 비었거나 맞는 사람이 없을 때 | 아무 일도 일어나지 않는다. 모두 "준비 중" 화면을 본다 |

- 번호 값은 저장소·로그·화면에 넣지 않는다(저장소는 공개다).
- "HR 0명 확인 → 지정"은 한 트랜잭션에서 한다.
- 판정은 `resolve_sso_user`처럼 순수 함수로 만들어 selfcheck에서 검증한다: HR이 있으면 번호가 같아도 지정되지 않는다 · 값이 비면 지정되지 않는다 · 번호가 다르면 지정되지 않는다 · 마지막 HR은 화면에서 빠지지 않는다.

## 5. 보안 설계

| 위협 | 대응 |
|---|---|
| **token이 로그에 남는다** — nginx 기본 로그는 주소 전체(`?token=`)를 기록한다 | `/api/auth/hiworks` 위치만 **쿼리 없이 기록**하는 로그 형식을 쓴다. Flask 쪽 로그에도 token을 찍지 않는다 |
| **token이 다른 사이트로 샌다** (Referer) | 수신 즉시 302로 token 없는 주소로 보내고, `Referrer-Policy: no-referrer` |
| **token 재사용** — 하이웍스 token은 60초 유효이고 그 안에는 **다시 쓸 수 있다**(#65 답변 3) | 사용한 token의 해시를 `sso_used_tokens`에 **60초** 보관하고 재사용을 거부한다(#65 결정 ③ — token 유효시간과 같게). **하이웍스에 묻기 전에 먼저 기록한다**(§3 ②) — `token_hash`가 기본 키라, 같은 token이 거의 동시에 두 번 와도 DB가 하나만 받아 준다. 하이웍스가 막아 주지 않으므로 포털의 재사용 거부가 **꼭 필요하다** |
| 가짜 확인 서버 | 확인 주소는 코드에 고정(`link-api.hiworks.com`), HTTPS 인증서 검증, 리다이렉트 불허 |
| 수신 경로 두드리기 (무작위 token 대입) | **실제 접속자 주소(`CF-Connecting-IP` 헤더)**당 1분 30회 초과 시 429. 포털은 Cloudflare를 거쳐 들어오므로 서버가 보는 접속 주소는 전 직원이 같다 — 그 주소로 세면 여러 명이 동시에 메뉴를 누를 때 전원이 막힌다. 서버는 밖에서 Cloudflare로만 들어올 수 있어 이 헤더를 믿을 수 있다. **nginx가 이 헤더를 api로 넘긴다**(`/api/` 위치에 명시). 세션에 남기는 접속 IP(`sessions.ip`)도 같은 값을 쓴다. **횟수는 SQLite에 센다**(§6 `sso_rate_hits`) — 서버 프로그램(gunicorn)이 2개로 돌아서 각자 메모리에 세면 숫자가 나뉜다. token은 하이웍스가 발급하므로 대입 성공 가능성은 낮지만, 포털이 link-api를 과도하게 호출하지 않게 막는다 |
| 세션 고정 | 로그인마다 새 세션 토큰을 만든다. 로그인 전 쿠키 값을 이어 쓰지 않는다 |
| CSRF | 쿠키 `SameSite=Lax` + 상태를 바꾸는 API는 POST 전용 + `Origin` 헤더가 포털 주소인지 검사 |
| 역할 위조 | 직책·HR 권한·포털 사용은 포털 DB에서만 읽는다. 하이웍스 응답·화면 값으로 판단하지 않는다 |

**오피스 토큰은 로그인에 필요 없다.** link-api 조회에는 인증 헤더가 없다. 오피스 토큰은 알림·전자결재·**명단 동기화(§11)**에서만 쓴다. 그래서 **로그인 경로는 오피스 토큰 없이 PC에서 만들고 시험할 수 있다** (설정 가이드 3장과 같은 결론). 오피스 토큰이 필요한 것은 명단 동기화의 실제 호출뿐이고, 그 시험은 포털 서버에서 한다(§8).

### 겸직 C — 구조는 열어 두고 운영은 막는다 (#32 4번, 2026-10-12 확정)

8월 설계는 `users.role` 한 칸, 곧 "한 사람 = 역할 하나"였다(8월 설계 §4 가정). 인사담당자가 **C(지금은 없지만 앞으로 생길 수 있다)**로 정했다. 직원 정보는 로그인 구현 때 처음 저장되므로 지금 바꾸면 옮길 자료가 없다.

| 구분 | 내용 |
|---|---|
| 구조 | `user_roles`에 한 사람이 역할을 여러 줄 가질 수 있다 |
| 운영 | **당분간 직책 겸직 금지.** 구성원 설정 기능(도메인 규칙 한 곳)이 두 번째 직책을 거부한다. DB 제약으로 막지 않는다 — 나중에 풀 때 저장된 직원 정보를 옮기지 않기 위해서다. **HR 권한은 겸직으로 치지 않는다**(아래 "사람별 설정") |
| 줄이 없는 사람 | 직책이 없는 직원이다. 들어올 수 있는지는 `users.portal_enabled`가 정한다(§4) |
| `Actor(user_id, role)` | **직책과 HR 권한을 함께 담도록 고친다**(아래 "사람별 설정"). 직책 겸직을 풀 때는 다시 여러 직책 기준으로 고쳐야 한다 — 그때 고치는 것은 코드뿐이고 저장된 자료는 그대로다 |

### 사람별 설정 — 직책은 하나, HR 권한은 따로 (2026-10-12 추가, 인사담당자 확정)

하이웍스에는 직책이 없다(§2). HR이 포털에서 사람마다 아래 여섯 가지를 정한다. 화면은 조직도 > 구성원 설정이고, 시연 화면이 PR #115에 있다.

| 칸 | 값 | 저장 |
|---|---|---|
| 포털 사용 | 켬 / 끔 | `users.portal_enabled`. **시범 사용자 명단 = 켜진 사람**(§4). 명단 동기화가 올린 새 사람은 꺼져 있다(§11) |
| 직책 | 없음 · 팀장 · 본부장 · 대표이사 중 **하나** | `user_roles`의 `TEAM_LEADER`·`DIVISION_HEAD`·`CEO` 중 한 줄. 없으면 줄이 없다 |
| HR 권한 | 있음 / 없음 | `user_roles`의 `HR_ADMIN` 줄. **직책과 함께 가질 수 있다** |
| KPI 작성 | 함 / 안 함 | `users.writes_kpi`. 안 함 = 현장직(팀장 평가). 대표이사는 항상 안 함(경영계획 목표만) |
| 평가 대상 | 대상 / 아님 | `users.in_evaluation`. **본부장·대표이사는 항상 아님**(2026-10-13) — 직책이 본부장·대표이사인 사람은 켤 수 없다 |
| 연봉계약서 | 대상 / 아님 | `users.has_contract`. **본부장·대표이사는 항상 아님**(2026-10-13) |

- **왜 넷 중 하나로 고르지 않는가**: 인사담당자의 기준은 "직책은 한 사람에 하나, HR만 예외"다. HR 팀장은 팀장이면서 HR이고, HR 담당자는 직책 없이 HR이다. 둘 다 본인 KPI를 쓴다. 넷 중 하나를 고르는 방식으로는 HR 팀장을 담을 수 없다 — 팀장을 고르면 HR 화면을, HR을 고르면 팀원 KPI 승인을 못 쓴다.
- **겸직 C와의 관계**: 직책 겸직(팀장 둘, 본부장 겸 팀장)은 여전히 막는다. HR 권한은 겸직으로 치지 않는다.
- **규칙** (구성원 설정 기능 한 곳이 지킨다): 팀장은 팀에 한 명, 본부장은 본부에 한 명, 대표이사는 한 명 · HR 권한이 있고 포털 사용이 켜진 활성 사용자가 한 명뿐이면 그 사람의 HR 권한·포털 사용을 끌 수 없다(§4 "첫 HR 담당자") · KPI 작성은 그 사람의 평가가 시작된 뒤에는 바꿀 수 없다 · 바꾼 내용은 감사로그에 남긴다.
- **`Actor`가 바뀐다**: `Actor(user_id, role)` 한 칸으로는 HR 팀장을 나타낼 수 없다. 직책과 HR 권한을 함께 담도록 고치고, 권한 판정(`access.py`)은 **새로 만든다**(아직 파일이 없다, §8 2단계). 감사 로그의 역할 칸도 같은 두 칸으로 바꾼다(위 SQL, 감사 기록 `AuditEntry`도 함께). 8월 도메인 코드와 selfcheck(44건)가 영향을 받는다. `writes_kpi`·`in_evaluation`·`has_contract`는 평가·계약 유스케이스가 읽는다(예: 평가 대상이 아니면 본부 인원 N에서 빠진다).
- 8월 설계의 `EMPLOYEE` 역할은 없앤다(감사 로그의 역할 칸에서도) — 직책 줄이 없는 사람이 직원이고, 출입은 `portal_enabled`가 정한다. 대표이사(`CEO`)는 새로 더한다(KPI 현황에서 본부장·팀장 KPI를 조회). **2026-10-13부터 조회만 하지 않는다** — 아래 "평가에서 누가 무엇을 하나".
- **인사담당자 확정**(2026-10-13, #116 답변): 대표이사는 평가 대상·연봉계약서 대상이 아니다 / 평가 대상과 KPI 작성은 서로 따로 정한다. 대표이사의 급여·계약 화면은 아직 정하지 않았다(지금은 자료 없음으로 둔다).

### 평가에서 누가 무엇을 하나 (2026-10-13 추가, 인사담당자 확정)

8월 설계의 권한 표(등급 배정은 본부장, 확정은 HR)를 아래로 바꾼다. 규칙 원본은 `2026-09-21-kpi-goal-screen-design.md` 8장이고, 시연 화면이 PR #122에 있다.

- **본부장과 대표이사는 평가받지 않는다.** 본부장은 KPI만 쓴다.
- 등급 비율을 함께 쓰는 **묶음**이 셋이다: 본부 팀원(본부마다, 팀장·본부장 제외) · 전사 팀장 · 직속부서 팀원.
- 순서는 하나다: 자기평가 → 평가자(점수 + 등급 의견) → 등급 배정 → **대표이사 확인** → **HR 확정** → 결과 공개.

| 하는 일 | 팀장 | 본부장 | 대표이사 | HR 권한 |
|---|---|---|---|---|
| KPI 승인 | 자기 팀원 | 자기 본부의 팀장·팀원 | **본부장 · 직속부서 팀장** (HR 확인 단계는 없어졌다) | 맡겨졌을 때만 대신 |
| 평가 (점수 + 등급 의견) | 자기 팀원 | 자기 본부의 팀장 | 직속부서 팀장 | 맡겨졌을 때만 대신 (HR 팀장은 팀장으로서 자기 팀원) |
| 등급 배정 · 마감 | — | 자기 본부 팀원 (팀장 점수도 고칠 수 있다) | 직속부서 팀원 | 맡겨졌을 때만 대신 |
| 묶음 확인 | — | — | 모든 묶음. 전사 팀장은 고칠 수 있고, 본부 팀원은 고치지 않고 본부장에게 돌려보낸다 | 맡겨졌을 때만 대신 |
| 묶음 확정 · 되돌리기 · 결과 공개 | — | — | — | 한다 |
| 기간 · 기준 점수 · 근태 · 평가 제외 · 자기평가 없이 진행 | — | — | — | 한다 |
| 이의 신청 | — | — | 등급을 바꾸는 답변만 확인 | 답변한다 |
| 결과 조회 | 자기 팀원 | 자기 본부 | 전체 | 전체 |

권한 판정(`access.py`)은 직책·HR 권한에 더해 **대상이 어느 묶음이고 지금 어느 단계인가**를 함께 본다. 예: 본부장은 자기 본부 팀원의 등급을 "배정 단계"에서만 고칠 수 있고, 대표이사는 그 묶음을 고칠 수 없다.

### HR에 맡기기 — 대표이사의 일을 HR이 대신 (2026-10-13 추가, 인사담당자 확정)

대표이사가 포털에서 **"HR에 맡기기"를 켜야** HR 권한자가 대표이사의 일(위 표의 "맡겨졌을 때만 대신")을 할 수 있다. HR이 스스로 켤 수 없다.

- 저장: 맡김 상태 한 칸(켜짐·켠 사람·켠 시각)과 감사로그. 대신 한 일에는 **실제로 입력한 사람**(`user_id`)을 대표이사와 함께 남긴다.
- **본인의 것은 대신 할 수 없다** — HR 팀장 본인의 평가·KPI 승인, HR 담당자 본인의 등급은 다른 HR이나 대표이사가 한다.
- 꺼지면 그 순간부터 대신 할 수 없다. 이미 한 일은 되돌리지 않는다.

### 결과 공개 전 열람 제한 (2026-10-13 추가, 인사담당자 지적)

HR이 결과를 공개하기 전에는 등급이 새면 안 된다. **화면에서 가리는 것으로는 부족하고, 서버 응답에서 빼야 한다.**

| 보는 사람 | 공개 전에 받는 것 |
|---|---|
| 본인 | 자기가 낸 자기평가만 |
| 평가자 (팀장 · 팀장을 평가한 본부장) | **자기가 낸 점수와 등급 의견만.** 윗사람이 고쳤다는 사실은 알리되 고친 내용과 최종 등급은 주지 않는다 |
| 등급을 정하는 사람 (본부장 — 자기 본부 팀원) · 대표이사 · HR | 전부 |

## 7. 개발·검증 방법 (시험용 하이웍스가 없다)

가비아는 시험용 오피스를 제공하지 않는다. 그래서 단계를 나눈다.

| 단계 | 방법 | 실제 하이웍스 |
|---|---|---|
| 1. 로직 | `resolve_sso_user`, token 형식 검사, 재사용 검사를 selfcheck로 검증 | 불필요 |

## 9. 개발본부장 검토 요청 항목

8월 설계 §11의 여섯 가지를 아래로 바꾼다.

1. **token 취급** — 로그(nginx·Flask)에 남지 않는가, 302로 주소에서 지워지는가, `Referrer-Policy`가 붙는가
2. **token 재사용 거부** — 하이웍스에 묻기 전에 먼저 기록하는가, 같은 token이 동시에 두 번 와도 하나만 통과하는가
3. **확인 서버 고정** — link-api 주소가 코드 고정·HTTPS 검증·리다이렉트 불허인가, 운영 모드에 `HIWORKS_LINK_API_BASE`가 있으면 서버가 시작을 거부하는가
4. **사람 연결 규칙** — 이미 연결된 사람을 사번으로 가로챌 수 없는가, 미등록·비활성 안내가 같은 문구인가, (사번 연결 대안을 쓸 때) 이름까지 같아야 연결되고 `SSO_LINK`로 남는가
5. **세션** — 쿠키 세 플래그, 토큰 해시 저장, 비활성화 시 즉시 폐기, **로그인마다 새 세션 발급**(로그인 전 쿠키 값을 이어 쓰지 않는다), 최대 상한(발급 후 12시간), 세션이 없으면 이미 있는 API도 401인가(§3)
6. **`PRAGMA foreign_keys = ON`** — 연결 직후 가장 먼저 켜지는가 (#35 정정 ②)
7. **백업** — 8월 설계 §9 + #36 항목 7·8
8. **사람별 설정·시범 사용자 명단** — 직책은 한 줄만 들어가는가(두 번째 직책 거부), HR 권한은 직책과 함께 가질 수 있는가, `Actor`가 직책과 HR 권한을 함께 담고 권한 판정이 그에 맞는가(HR 팀장이 팀장 권한과 HR 권한을 모두 쓰는가), 포털 사용이 꺼진 사람(시범 사용자 명단 밖)이 세션을 받지 못하고 "준비 중" 화면을 보는가, 저장 모양(`user_roles` 줄 + `users` 칸)이 적절한가, 감사 로그에 직책과 HR 권한이 두 칸으로 남는가(대표이사 포함, `EMPLOYEE` 없음) (§4·§6)
9. **명단 동기화** — 조회 실패·빈 응답일 때 아무도 비활성화되지 않는가, 비활성인 사람을 다시 켜지 않는가, 사람별 설정을 건드리지 않는가 (§11)
10. **전자서명 기록 파기** — 서명 완료 계약의 수정 금지 장치를 유지하면서 기한이 지난 서명 그림·접속 IP만 지울 수 있는가, 감사 로그에 서명 접속 IP가 들어가지 않는가 (§12)
11. **요청 빈도 제한** — `CF-Connecting-IP` 기준으로 세는가, nginx가 그 헤더를 api로 넘기는가, 횟수를 SQLite에 세어 서버 프로그램 2개가 같은 숫자를 보는가, 여러 직원이 동시에 메뉴를 눌러도 서로 막히지 않는가 (§5)
12. **다른 사이트에서 몰래 보내는 요청 막기(CSRF)** — 상태를 바꾸는 API가 POST 전용이고 `Origin` 헤더를 검사하는가 (§5)
13. **첫 HR 담당자 지정** — HR이 한 명이라도 있으면 서버 설정값이 무시되는가, 하이웍스 사용자 번호로만 맞추는가, 마지막 HR을 화면에서 빼거나 비활성화할 수 없는가, 지정이 감사로그에 남는가 (§4)
14. **대표이사 권한과 HR에 맡기기** — 대표이사가 승인·평가·확인을 하는 범위가 §6 표와 같은가, 맡김이 꺼져 있을 때 HR이 대표이사의 일을 못 하는가, 맡김을 HR이 켤 수 없는가, 대신 한 일에 실제 입력자가 남는가, HR 본인의 것을 대신 할 수 없는가 (§6)
15. **결과 공개 전 열람 제한** — 평가자에게 가는 응답에 윗사람이 고친 점수와 최종 등급이 들어 있지 않은가, 본인에게 가는 응답에 공개 전 점수·등급이 없는가 (§6)

## 11. 직원 명단 동기화 (2026-10-12 추가)

하이웍스에서 직원 명단·조직을 가져올 수 있다(2026-10-03 실측, 설정 가이드 5장 "조직도"). HR이 직원을 포털에 하나하나 입력하지 않고 **서버가 하루 1회 가져온다.** 흐름 그림은 설정 가이드 5장 "그림으로 보기" ④.

| 항목 | 내용 |
|---|---|
| 언제 | 서버가 **하루 1회** (하이웍스 호출 한도는 회사당 하루 1,000건 — 동기화는 한 번에 2건) |

- **하이웍스가 먼저 알려 주는 기능은 확인되지 않았다.** 그래서 포털이 하루 1회 물어본다. 입사·이동은 다음 동기화 때 반영되고, 퇴사는 기다리지 않고 HR이 당일에 비활성화한다(§4).
- 조직 조회의 사용자 번호가 SSO의 `user-no`와 같은 번호 체계인지는 첫 실연결 때 확인한다(§7 3단계). 다르면 §4의 대안을 쓴다.
- 지금 스키마의 `users.employee_no`·`hire_date`는 비울 수 없는 칸인데 하이웍스 조직 조회에는 둘 다 없다. 동기화로 들어온 행을 위해 **비울 수 있게 바꾼다**(`employee_no`의 중복 금지는 유지). 채우는 방법은 §10.
- 본부·팀도 하이웍스 조직을 따라 고친다. 그러려면 하이웍스 조직과 포털 부서(`departments`)를 짝지어 두어야 한다. 하이웍스 조직은 21개(회사 1 + 20개, 2단계)로 포털 조직도(본부 6·팀 14)와 개수가 같다. 짝짓는 칼럼과 이름 대응은 구현 PR(§8 3단계)에서 확정한다. → 아래 "3단계에서 정한 것".
- 비교 규칙(추가·소속 변경·비활성 목록 만들기)은 `resolve_sso_user`처럼 순수 함수로 만들어 DB·하이웍스 없이 selfcheck에서 검증한다. 오피스 토큰이 필요한 실제 호출 시험은 포털 서버에서 하고(§8), 토큰 값과 직원 정보 값은 출력하지 않는다.

### 3단계에서 정한 것 (2026-10-15, 구현 `domain/roster.py` · `roster_sync.py` · `sql/003_roster_sync.sql`)

## 12. 전자서명 기록 보관 (2026-10-12 추가, #32 6번 확정)

연봉계약서에 서명할 때 서명 그림과 접속 IP를 함께 남긴다. 둘 다 개인정보라 보관 기한을 둔다. [평가·계약 설계](2026-08-24-hr-evaluation-contract-design.md)는 "무기한 보관, 보관기간이 정해지면 파기 절차를 추가한다"였다.

| 항목 | 내용 |
|---|---|
| 보관 기한 | **계약 종료 후 3년** (`salary_contracts.contract_ends_on` 기준) |
| 기한이 지나면 지우는 것 | **서명 그림**(`signature_image`)과 **접속 IP**(`signer_ip`) — 이 둘만 |
| 남기는 것 | 계약서(본문·금액·기간)와 **"누가 언제 서명했다"** 기록(`signer_user_id`·`signer_name`·`signed_at`), 문서 해시(`document_hash`) |

구현할 때 풀어야 할 것 — 지금 스키마는 "서명 완료된 계약은 고칠 수 없다"로 잠겨 있다.

- `contract_signed_chk`는 서명 완료 계약에 서명 그림·접속 IP가 **반드시 있어야** 한다고 검사한다 → 파기한 날짜 칸을 두고, 그 칸이 채워진 계약은 두 값이 비어 있어도 되게 바꾼다.
- `trg_contract_lock_frozen`은 서명 완료 계약의 계약 내용·서명 기록 칸을 고치지 못하게 막는다 → **기한이 지난 계약에서 이 두 값을 비우는 것 하나만** 허용한다. 그 밖의 수정은 지금처럼 막는다.
- 파기하면 감사 로그에 남긴다(어느 계약에서 언제 지웠는지. 지운 값은 남기지 않는다).
- **감사 로그에는 서명 때의 접속 IP를 적지 않는다**(2026-10-15 재검토). 감사 로그는 고치거나 지울 수 없게 막아 두는 것이 원칙이라, 나중에 지워야 할 값은 처음부터 넣지 않는다. 접속 IP는 계약(`signer_ip`)에만 두고 기한이 되면 거기서 지운다. 지금 서명 기능은 `CONTRACT_SIGNED` 기록의 `ip`에 이 값을 넣고 있으므로 이 장을 구현할 때 함께 뺀다.
- 계약서 PDF에 서명 그림이 찍힌다면 PDF도 같은 기한의 대상이다. PDF 생성은 아직 구현 전이므로 만들 때 이 기한을 반영한다.

구현 시점은 로그인과 별개다. **연봉계약서를 실제로 저장하기 전**에 넣는다(#32).
