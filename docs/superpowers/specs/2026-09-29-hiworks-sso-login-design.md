## 1. 무엇이 바뀌나

8월 설계는 "이메일 + 비밀번호로 직접 로그인"이었다. 가비아 회신과 API 문서 확인 결과 **하이웍스 "SSO 외부로 연동"**을 쓸 수 있으므로 로그인을 하이웍스에 맡긴다.

- 직원은 하이웍스에 로그인한 상태에서 **하이웍스 화면의 "인사포털" 메뉴**를 누른다.
- 하이웍스가 포털로 1회용 확인표(token)를 붙여 보낸다.
- 포털 서버가 그 확인표를 하이웍스에 되물어 **누구인지(사용자 번호·아이디·이름·사번)** 확인하고 포털 세션을 발급한다.
- **포털은 비밀번호를 받지도, 저장하지도 않는다.**

OAuth(포털 화면에 "하이웍스로 로그인" 버튼)는 문서상 지원 중단이고 가비아도 불가로 회신했다. 그래서 **출입구는 하이웍스 메뉴 하나**다.

## 2. 하이웍스 쪽 사실 (API 문서·가비아 회신)

| 항목 | 내용 |
|---|---|
| 등록 위치 | [오피스 관리 > 서비스 연동(API) > SSO 관리 > 외부로 연동]에 연동 URL 등록 → [인트라넷 메뉴 추가]에서 그 SSO를 메뉴로 노출 |
| 연동 URL | `https://hr.abyz-lab.work/api/auth/hiworks` (설정 가이드 1장 E에서 확정) |
| 포털이 받는 요청 | `GET /api/auth/hiworks?token={token}` |
| 확인 API | `GET https://link-api.hiworks.com/v4/tokens/{token}` — **인증 헤더 없음, 오피스 토큰 불필요** |
| 응답 | `data.user-no`(고유·불변), `data.user-id`(계정 아이디), `data.user-name`, `data.employee-no`(사번) |
| 문서에 없는 것 | 토큰 유효시간, 1회용인지 여부, 소속·직급 정보 |

**소속·직급이 오지 않는다.** 그래서 팀장·본부장·HR 같은 **역할은 포털 DB가 정한다.** 하이웍스 값으로 권한을 판단하지 않는다.

## 3. 로그인 흐름

```
[직원] 하이웍스 로그인 → "인사포털" 메뉴 클릭
   │
   ▼
GET /api/auth/hiworks?token=T
   │
   ├─ ① 형식 검사: T가 비었거나 이상한 문자 → 400 안내 화면
   ├─ ② 재사용 검사: sha256(T)가 sso_used_tokens에 있으면 → 거부 (§5)
   ├─ ③ link-api 조회 (HTTPS, 5초 타임아웃, 리다이렉트 따라가지 않음)
   │       실패·빈 응답 → "하이웍스 확인에 실패했습니다. 메뉴를 다시 눌러주세요"
   ├─ ④ sha256(T)를 sso_used_tokens에 기록
   ├─ ⑤ 사용자 찾기 (§4)
   │       못 찾음 → "인사포털에 등록되지 않은 사용자입니다. 인사팀에 문의하세요" (403)
   │       비활성 → 같은 문구 (등록 여부를 구분해 알려주지 않는다)
   ├─ ⑥ 세션 발급 (새 토큰, sessions에 해시 저장), last_login_at 갱신, 감사로그 LOGIN
   └─ ⑦ 302 → "/"  (주소창에서 token을 지운다)
        응답 헤더: Referrer-Policy: no-referrer, Cache-Control: no-store

[요청마다] 쿠키 → 세션 조회 → 만료·폐기·사용자 비활성 확인 → Actor(user_id, role)
```

**포털 주소로 바로 들어온 경우** (세션 없음): 화면 전체를 가리고 "하이웍스에서 **인사포털** 메뉴로 들어와 주세요" 안내와 하이웍스 로그인 주소 링크를 보여준다. 정적 페이지(`public/`)는 누구나 받을 수 있지만, **데이터는 전부 `/api/*`에서 세션 검사를 거친다.** 화면을 가리는 것은 안내일 뿐 보안이 아니다(8월 설계 §8 "세 겹").

**로그아웃**은 포털 세션만 폐기한다. 하이웍스는 로그인 상태로 남으므로 메뉴를 다시 누르면 바로 들어온다. 공용 PC에서는 하이웍스도 로그아웃해야 한다고 로그아웃 화면에 적는다.

## 4. 사람 연결 규칙

```
1. users.hiworks_user_no = data.user-no 인 행 → 그 사람
2. 없으면 users.employee_no = data.employee-no 이고 hiworks_user_no IS NULL 인 행
   → 그 사람. 이때 hiworks_user_no를 저장한다 (첫 로그인 연결)
3. 둘 다 없으면 → 미등록
```

- **`user-no`를 1순위로 쓰는 이유**: 사번은 오타·변경이 있을 수 있지만 `user-no`는 하이웍스가 계정마다 붙이는 고유 번호다. 첫 로그인 때 한 번 사번으로 맞춘 뒤로는 번호로만 찾는다.
- 2번에서 `hiworks_user_no IS NULL` 조건을 두는 이유: 이미 다른 하이웍스 계정과 연결된 사람을 사번만 같다고 가로채지 못하게 한다.
- 사번이 비어 있는 하이웍스 계정은 2번이 실패하므로 미등록으로 처리된다. HR이 하이웍스에 사번을 넣어야 한다.
- **자동 가입은 없다.** 하이웍스 계정이 있어도 포털 `users`에 HR이 등록해야 들어온다. 역할을 모르는 사람을 들이지 않는다.
- **비활성화**: HR이 포털에서 사용자를 비활성화하면 그 사람의 세션을 **즉시 전부 폐기**한다. 하이웍스 계정 정지만으로는 이미 발급된 포털 세션(최대 12시간)이 끊기지 않으므로, 퇴사 처리 순서에 "포털 비활성화"를 넣는다.

이 연결 규칙은 순수 함수 `resolve_sso_user(token_data, users) -> 결과`로 만들어 DB 없이 selfcheck에서 검증한다.

## 5. 보안 설계

| 위협 | 대응 |
|---|---|
| **token이 로그에 남는다** — nginx 기본 로그는 주소 전체(`?token=`)를 기록한다 | `/api/auth/hiworks` 위치만 **쿼리 없이 기록**하는 로그 형식을 쓴다. Flask 쪽 로그에도 token을 찍지 않는다 |
| **token이 다른 사이트로 샌다** (Referer) | 수신 즉시 302로 token 없는 주소로 보내고, `Referrer-Policy: no-referrer` |
| **token 재사용** — 1회용인지 문서에 없다 | 사용한 token의 해시를 `sso_used_tokens`에 24시간 보관하고 재사용을 거부한다. 하이웍스가 이미 1회용이어도 손해가 없다 |
| 가짜 확인 서버 | 확인 주소는 코드에 고정(`link-api.hiworks.com`), HTTPS 인증서 검증, 리다이렉트 불허 |
| 수신 경로 두드리기 (무작위 token 대입) | IP당 1분 30회 초과 시 429. token은 하이웍스가 발급하므로 대입 성공 가능성은 낮지만, 포털이 link-api를 과도하게 호출하지 않게 막는다 |
| 세션 고정 | 로그인마다 새 세션 토큰을 만든다. 로그인 전 쿠키 값을 이어 쓰지 않는다 |
| CSRF | 쿠키 `SameSite=Lax` + 상태를 바꾸는 API는 POST 전용 + `Origin` 헤더가 포털 주소인지 검사 |
| 역할 위조 | 역할은 포털 DB에서만 읽는다. 하이웍스 응답·화면 값으로 판단하지 않는다 |

**오피스 토큰은 로그인에 필요 없다.** link-api 조회에는 인증 헤더가 없다. 오피스 토큰은 알림·전자결재·조직 조회 단계에서만 쓴다. 그래서 **로그인 구현은 오피스 토큰 발급을 기다리지 않고 시작할 수 있다** (설정 가이드 3장과 같은 결론).

## 6. 테이블 변경

8월 설계 §6.1의 비밀번호 칼럼 대신 아래를 추가한다.

```sql
-- users 에 추가
    hiworks_user_no TEXT NULL UNIQUE,   -- 첫 로그인 때 채운다. 하이웍스 고유 번호
    last_login_at   TEXT NULL,
    deactivated_at  TEXT NULL,

-- 8월 설계 §6.2 sessions 그대로 (token_hash, user_id, created_at, last_seen_at,
--                                  expires_at, ip, user_agent, revoked_at)

CREATE TABLE sso_used_tokens (
    token_hash TEXT PRIMARY KEY,         -- sha256(token). 원본은 저장하지 않는다
    used_at    TEXT NOT NULL
);
-- 24시간 지난 행은 로그인 처리 때 함께 지운다 (별도 배치 불필요)
```

`users.email`은 `NOT NULL UNIQUE`로 남는다. 알림·메일 발송에 쓰고, 로그인 아이디로는 쓰지 않는다.

## 7. 개발·검증 방법 (시험용 하이웍스가 없다)

가비아는 시험용 오피스를 제공하지 않는다. 그래서 단계를 나눈다.

| 단계 | 방법 | 실제 하이웍스 |
|---|---|---|
| 1. 로직 | `resolve_sso_user`, token 형식 검사, 재사용 검사를 selfcheck로 검증 | 불필요 |
| 2. 경로 | 서버 설정 `HIWORKS_LINK_API_BASE`로 확인 주소를 **로컬 가짜 서버**로 바꿔 전체 흐름을 시험. 운영에서는 이 값을 두지 않아 기본값(`https://link-api.hiworks.com`)만 쓴다 | 불필요 |
| 3. 실연결 | 하이웍스 API 담당자가 SSO 연동 URL만 등록(메뉴는 아직 안 만듦) → **시험용 계정 1개**로 연동 URL을 직접 열어 확인. token 유효시간·1회용 여부도 이때 측정 | 필요 |
| 4. 공개 | "로그인 준비 완료" 통보 → 인트라넷 메뉴 등록 → 모바일 앱 노출 확인 | 필요 |

`HIWORKS_LINK_API_BASE`는 개발용 우회로다. 운영 서버 `.env`에 이 값이 있으면 서버 시작 시 경고를 기록한다.

## 9. 개발본부장 검토 요청 항목

8월 설계 §11의 여섯 가지를 아래로 바꾼다.

1. **token 취급** — 로그(nginx·Flask)에 남지 않는가, 302로 주소에서 지워지는가, `Referrer-Policy`가 붙는가
2. **token 재사용 거부** — `sso_used_tokens`가 동작하는가
3. **확인 서버 고정** — link-api 주소가 코드 고정·HTTPS 검증·리다이렉트 불허인가, `HIWORKS_LINK_API_BASE`가 운영에 없는가
4. **사람 연결 규칙** — 이미 연결된 사람을 사번으로 가로챌 수 없는가, 미등록·비활성 안내가 같은 문구인가
5. **세션** — 쿠키 세 플래그, 토큰 해시 저장, 비활성화 시 즉시 폐기
6. **`PRAGMA foreign_keys = ON`** — 연결 직후 가장 먼저 켜지는가 (#35 정정 ②)
7. **백업** — 8월 설계 §9 + #36 항목 7·8
