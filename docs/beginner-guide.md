# 초심자 가이드 — 인사 통합포털 만들기

이 문서는 **개발을 한 번도 해본 적 없는 분**을 위한 것이다.

프로그램을 설치할 필요도, 어려운 명령어를 외울 필요도 없다.
**인터넷 브라우저 하나면 된다.**

읽는 순서대로 따라 하면 된다. 건너뛰지 않는 것을 권한다.

---

## 시작하기 전에

### 준비물

| 항목 | 설명 |
|---|---|
| 인터넷 브라우저 | Chrome, Edge 등 평소 쓰는 것 |
| 이메일 주소 | 회사 메일 권장 |
| 휴대폰 | 2단계 인증에 필요하다 |
| GitHub 계정 | **없으면 2장에서 만든다** |

**이게 전부다.** 서버 접속도, 프로그램 설치도 필요 없다.

### 먼저 안심하고 시작하자

처음 하는 분들이 가장 걱정하는 것은 **"내가 뭔가 잘못 건드려서 망가뜨리면 어쩌지"** 다.

그런 일은 일어나지 않는다. 이유는 이렇다.

1. **당신이 고친 내용은 곧바로 실제 사이트에 반영되지 않는다.** 반드시 "확인 요청"이라는 중간 단계를 거친다
2. **자동 검사기가 먼저 확인한다.** 문제가 있으면 빨간 X가 뜨고 진행이 막힌다
3. **미리보기 화면으로 눈으로 확인할 수 있다.** 반영 전에 결과를 볼 수 있다
4. **사람이 한 번 더 승인해야 반영된다**
5. **모든 변경 기록이 남아 있어서 언제든 되돌릴 수 있다**

그러니 **마음 편히 시도해도 된다.** 잘못 고쳐도 되돌리면 그만이다.

### 혼자 코드를 다 쓰지 않아도 된다

이 가이드는 **AI 도구(Claude 등)와 함께 작업하는 것**을 전제로 한다.
당신이 할 일은 네 가지다.

1. **무엇을 만들지 정한다** — 사람만 할 수 있는 일이다
2. **AI에게 정확히 요청한다** — 8장에서 방법을 알려준다
3. **결과를 눈으로 확인한다**
4. **승인을 요청한다**

코드를 한 줄도 못 써도 진행할 수 있다.
다만 **무엇이 어떻게 돌아가는지는 이해해야 한다.** 그래야 잘못된 결과를 알아챈다.

# 1장. 큰 그림

## 1-1. 우리가 만드는 것

회사 직원들이 쓸 **인사 포털 웹사이트**다.
연차 신청, 급여명세서 조회, 출장 신청 같은 일을 한곳에서 처리하는 사이트다.

주소는 이것이다 → **https://hr.abyz-lab.work**

지금은 **화면만 있는 모형**이다. 버튼을 눌러도 아무 일도 일어나지 않는다.
앞으로 이걸 진짜로 동작하는 시스템으로 만들어 나간다.

## 1-2. 작업은 이렇게 흘러간다

```
 ① 브라우저에서 내용을 고친다
      ↓
 ② "확인해 주세요" 라고 요청을 만든다   ← 이걸 PR이라고 부른다
      ↓
 ③ 자동 검사기가 문제가 없는지 본다
      ↓
 ④ 미리보기 화면으로 눈으로 확인한다
      ↓
 ⑤ 담당자가 승인한다
      ↓
 ⑥ 실제 사이트에 반영된다  (자동)
```

**당신이 하는 일은 ①②④ 세 가지다.** 나머지는 자동이거나 다른 사람이 한다.

## 1-3. 알아야 할 단어는 4개뿐

어려운 용어가 많이 나오지만, 처음에는 이 4개만 알면 된다.

| 단어 | 쉽게 말하면 | 비유 |
|---|---|---|
| **저장소** (Repository) | 이 프로젝트의 모든 파일이 들어 있는 폴더 | 프로젝트 캐비닛 |
| **브랜치** (Branch) | 원본을 건드리지 않고 따로 작업하는 사본 | 원본을 복사해서 쓰는 연습장 |
| **PR** (Pull Request) | "제가 이렇게 고쳤는데 확인해 주세요" 라는 요청서 | 결재 상신 |
| **병합** (Merge) | 승인된 내용을 원본에 합치는 것 | 결재 완료 |

### 브랜치를 왜 쓰는가

원본 파일을 직접 고치면 위험하다. 고치는 도중에 사이트가 깨질 수 있다.

그래서 **원본을 복사해서** 그 복사본에서 작업한다. 그것이 브랜치다.
작업이 끝나고 확인을 받으면, 그때 원본에 합친다.

```
원본 (main)  ──────────────────────────────▶  항상 정상 동작
                  ╲                    ╱
                   ╲── 내 작업 사본 ──╱     ← 여기서 마음껏 고친다
                        (브랜치)
```

**당신이 브랜치에서 무엇을 하든 실제 사이트는 멀쩡하다.** 이것이 안심해도 되는 이유다.

# 2장. GitHub 계정 만들고 들어가기

## 2-1. GitHub이란

우리 프로젝트의 모든 파일과 변경 기록이 보관된 곳이다.
"회사 공용 문서함"이라고 생각하면 된다.

작업에 참여하려면 **본인 계정이 있어야 한다.** 누가 무엇을 고쳤는지 기록으로 남기기 위해서다.
계정은 무료이고, 만드는 데 5분이면 된다.

> 이미 계정이 있다면 **2-4절(초대 수락)** 로 건너뛴다.

## 2-2. 계정 만들기

### ① 가입 화면 열기

브라우저에서 아래 주소로 들어간다.

```
https://github.com/signup
```

### ② 정보 입력

순서대로 물어본다. 하나씩 입력하고 `Continue` 를 누르면 된다.

| 항목 | 무엇을 입력하나 | 주의할 점 |
|---|---|---|
| **Email** | 회사 이메일 주소 | 나중에 바꾸기 번거로우니 오래 쓸 주소로 |
| **Password** | 비밀번호 | 15자 이상 권장. **다른 곳과 다른 비밀번호를 쓴다** |
| **Username** | 사용자 이름 (아이디) | 영문·숫자·하이픈만 가능. 한글 불가 |
| **Email preferences** | 광고 메일 수신 여부 | `n` 입력 (안 받겠다는 뜻) |

**Username 정하는 요령**

전 세계에서 유일해야 해서 흔한 이름은 이미 쓰이고 있다. 이런 식으로 만든다.

```
hong-gildong-hnabyz
gd-hong-hna
```

> 사용자 이름은 다른 사람에게 보인다. 회사 업무용이므로 알아보기 쉬운 것으로 정한다.

### ③ 사람인지 확인

퍼즐을 맞추라는 화면이 나온다. 안내대로 하면 된다.

### ④ 이메일 인증

입력한 메일 주소로 **8자리 숫자**가 온다. 그 숫자를 입력한다.

> 메일이 안 오면 스팸함을 확인한다. 5분 이상 안 오면 다시 요청한다.

### ⑤ 설문은 건너뛴다

"어떤 용도로 쓰시나요" 같은 질문이 나오면 **`Skip personalization`** 을 누른다.
유료 플랜을 권하는 화면이 나와도 **무료(Free)** 를 선택한다. 우리 작업에는 무료로 충분하다.

여기까지 하면 계정이 만들어진다.

## 2-3. 2단계 인증 설정 (반드시 해야 한다)

**GitHub은 코드 작업에 참여하는 사람에게 2단계 인증을 의무화하고 있다.**
설정하지 않으면 일정 기간 뒤 작업이 제한된다. 미루지 말고 지금 한다.

2단계 인증이란, 비밀번호에 더해 **휴대폰으로 한 번 더 확인**하는 방식이다.
비밀번호가 유출돼도 계정을 지킬 수 있다.

### ① 휴대폰에 인증 앱 설치

아래 중 하나를 설치한다. 아무거나 하나면 된다.

- **Microsoft Authenticator**
- **Google Authenticator**

> 회사에서 이미 쓰는 인증 앱이 있다면 그것을 써도 된다.

### ② 설정 화면 열기

브라우저에서 아래 주소로 들어간다.

```
https://github.com/settings/security
```

**`Enable two-factor authentication`** 버튼을 누른다.

### ③ QR 코드 찍기

화면에 QR 코드가 나온다.

1. 휴대폰에서 인증 앱을 연다
2. `+` 또는 `계정 추가` 를 누른다
3. `QR 코드 스캔` 을 선택한다
4. 화면의 QR 코드를 비춘다

앱에 `GitHub` 항목이 생기고 **6자리 숫자**가 표시된다. 이 숫자는 30초마다 바뀐다.

### ④ 숫자 입력

앱에 보이는 6자리 숫자를 GitHub 화면에 입력한다.

> 숫자가 곧 바뀔 것 같으면 다음 숫자를 기다렸다가 입력한다.

### ⑤ 복구 코드 저장 — 이 단계를 빠뜨리면 안 된다

**`Recovery codes`** 라는 16자리 코드 여러 개가 나온다.

**이것은 휴대폰을 잃어버렸을 때 계정에 들어갈 수 있는 유일한 방법이다.**

- `Download` 를 눌러 파일로 저장한다
- 그 파일을 **안전한 곳**에 보관한다 (회사 문서함, 개인 금고 등)
- **절대 프로젝트 파일 안에 넣지 않는다**

> ⚠️ 복구 코드를 잃어버리고 휴대폰도 바꾸면 계정을 영영 못 쓰게 된다. 실제로 자주 일어나는 일이다.

## 2-4. 초대 수락하기

계정이 준비되면 관리자에게 알린다.

```
GitHub 계정 만들었습니다. 사용자 이름은 hong-gildong-hnabyz 입니다.
저장소에 초대 부탁드립니다.
```

관리자가 초대하면 **가입한 이메일로 초대 메일**이 온다.

1. 메일에서 **`View invitation`** 클릭
2. 열린 화면에서 **`Accept invitation`** 클릭

이제 저장소에 접근할 수 있다.

> 메일이 안 보이면 아래 주소에서 직접 확인할 수 있다.
> `https://github.com/hnabyz-bot/hr-portal/invitations`

## 2-5. 저장소 접속하기

브라우저 주소창에 아래를 입력한다.

```
https://github.com/hnabyz-bot/hr-portal
```

파일 목록이 보이면 성공이다.

> **"404 Not Found" 가 나온다면** 초대를 아직 수락하지 않았거나, 다른 계정으로 로그인되어 있는 것이다.
> 화면 오른쪽 위 프로필 아이콘을 눌러 어떤 계정으로 로그인되어 있는지 확인한다.

## 2-6. 화면 살펴보기

접속하면 파일 목록이 보인다. 우리 프로젝트에는 파일이 몇 개 없다.

| 이름 | 무엇인가 |
|---|---|
| **public** | 📁 폴더 — 실제 화면 파일이 들어 있다. **주로 여기를 고친다** |
| **docs** | 📁 폴더 — 설명 문서들 (이 가이드도 여기 있다) |
| **README.md** | 프로젝트 설명서와 할 일 목록 |
| **docker-compose.yml** | 서버 설정 파일 — **건드리지 않는다** |

화면 아래쪽에는 README.md 내용이 자동으로 펼쳐져 보인다.

## 2-7. 화면 파일 찾아보기

`public` 폴더를 클릭한다. 안에 `index.html` 파일 하나가 있다.

**이 파일 하나에 사이트 화면 전체가 들어 있다.** 클릭해서 열어보자.

알 수 없는 글자가 잔뜩 나오지만 당황할 필요 없다.
지금은 "아, 이 파일이구나" 정도만 알면 된다. 7장에서 구조를 설명한다.

# 3장. 첫 수정 해보기 (실습)

말로 설명하는 것보다 한 번 해보는 게 빠르다.
**실제 사이트에는 영향이 없는 안전한 연습**이니 편하게 따라 하자.

## 3-1. 파일 열기

1. https://github.com/hnabyz-bot/hr-portal 접속
2. `public` 폴더 클릭
3. `index.html` 클릭

## 3-2. 편집 모드로 들어가기

화면 오른쪽 위를 보면 **연필 모양 아이콘 ✏️** 이 있다. 그것을 클릭한다.

> 연필 아이콘 옆의 작은 `▼` 를 누르면 `Edit in place` 같은 항목이 나온다. 그냥 연필 아이콘을 바로 클릭하면 된다.

이제 글자를 고칠 수 있는 상태가 된다.

## 3-3. 고칠 부분 찾기

파일이 길어서 눈으로 찾기 어렵다. 검색 기능을 쓴다.

1. 키보드에서 **`Ctrl + F`** 를 누른다
2. 검색창에 아래를 입력한다

```
인사 통합포털
```

해당 글자가 있는 줄로 이동한다.

## 3-4. 글자 바꾸기

찾은 글자 중 하나를 이렇게 바꿔본다.

```
인사 통합포털   →   인사 포털 (연습)
```

평소 문서 고치듯이 클릭해서 지우고 입력하면 된다.

## 3-5. 저장 요청하기

화면 오른쪽 위 초록색 **`Commit changes...`** 버튼을 클릭한다.

창이 하나 뜬다. 여기가 중요하다.

**① 무엇을 바꿨는지 적는다**

`Commit message` 칸에 적는다. 나중에 이 문장만 보고 찾게 되므로 구체적으로 쓴다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 수정 | 사이드바 제목 문구 변경 |
| ㅇㅇ | 연차 신청 화면에 휴가 종류 선택 추가 |

**② 새 브랜치를 만든다 — 반드시 확인할 것**

창 아래쪽에 선택지가 두 개 있다.

```
○ Commit directly to the main branch          ← 이걸 고르면 안 된다
● Create a new branch for this commit and start a pull request   ← 이걸 고른다
```

**반드시 아래쪽(Create a new branch...)을 선택한다.**
위쪽은 원본을 직접 고치는 것이라 위험하다.

> 관리자가 보호 설정을 해두었다면 위쪽 선택지는 아예 비활성화되어 있을 수 있다. 그렇다면 신경 쓰지 않아도 된다.

브랜치 이름이 자동으로 채워진다 (`hnabyz-bot-patch-1` 같은 형태). 그대로 둬도 되고, 알아보기 쉽게 바꿔도 된다.

**③ `Propose changes` 버튼 클릭**

## 3-6. 확인 요청서(PR) 만들기

새 화면이 나온다. 여기서 **`Create pull request`** 버튼을 누르면 요청서가 만들어진다.

내용 칸에는 이런 것을 적으면 좋다.

```
사이드바 제목 문구를 바꿨습니다.
연습용이라 병합하지 않아도 됩니다.
```

**여기까지 하면 당신의 작업은 끝이다.** 이제 자동 검사가 시작된다.

## 3-7. 연습 정리하기

연습이었으므로 요청을 취소한다.

PR 화면 맨 아래로 내려가면 **`Close pull request`** 버튼이 있다. 그것을 누르면 요청이 취소된다.

**아무것도 반영되지 않았고, 아무것도 망가지지 않았다.**

여기까지 따라 했다면 기본은 끝난 것이다. 앞으로 하는 모든 작업이 이 순서의 반복이다.

# 4장. 검사 결과 읽는 법

PR을 만들면 자동 검사기가 돌아간다. 사람이 보기 전에 기계가 먼저 확인하는 단계다.

## 4-1. 표시 세 가지

PR 화면 아래쪽에 표시가 나타난다.

| 표시 | 뜻 | 할 일 |
|---|---|---|
| 🟡 **노란 점** | 검사 중 | 1~2분 기다린다 |
| ✅ **초록 체크** | 이상 없음 | 다음 단계로 |
| ❌ **빨간 X** | 문제 발견 | 아래 4-2 참고 |

## 4-2. 빨간 X가 나왔을 때

**당황할 필요 없다.** 이건 "이대로 반영하면 문제가 생기니 막았다"는 뜻이다. 오히려 잘 작동한 것이다.

무엇이 문제인지 확인하는 방법:

1. 빨간 X 옆의 **`Details`** 를 클릭한다
2. 검사 내용이 나온다. 빨간 글씨 부분이 문제다
3. **그 내용을 그대로 복사해서** AI나 담당자에게 보여준다

> **"안 돼요"라고만 말하지 않는다.** 에러 메시지를 그대로 복사해서 보여주면 훨씬 빨리 해결된다.

## 4-3. 자동 검사가 보는 것

무엇을 검사하는지 알아두면 실수를 미리 피할 수 있다.

| 검사 항목 | 왜 검사하는가 |
|---|---|
| 태그가 제대로 닫혔는지 | 하나만 빠져도 화면이 깨진다 |
| 비밀번호·인증키가 들어갔는지 | 한 번 올라가면 지워도 기록에 남는다 |
| 주민번호·실제 연락처가 들어갔는지 | 개인정보 사고를 막는다 |
| 글자가 깨지지 않는지 | 한글이 `????` 로 보이는 문제 |
| 사이트가 실제로 열리는지 | 파일 이름 오타 등 |

# 5장. 미리보기로 확인하기

코드를 못 읽어도 괜찮다. **화면으로 직접 보면 된다.**

PR을 만들면 그 PR 전용 미리보기 주소가 자동으로 만들어진다.

## 5-1. 미리보기 여는 법

PR 화면 아래쪽에 이런 댓글이 자동으로 달린다.

```
✅ 미리보기 준비됨
https://12.hr-portal.pages.dev
```

그 주소를 클릭하면 **내가 고친 내용이 반영된 화면**이 열린다.

## 5-2. 무엇을 확인할 것인가

- [ ] 고치려던 부분이 의도대로 바뀌었는가
- [ ] 다른 부분이 망가지지 않았는가
- [ ] 글자가 깨지지 않았는가
- [ ] 휴대폰으로 열어도 보이는가

## 5-3. 실제 사이트와 헷갈리지 말 것

| 주소 | 무엇인가 |
|---|---|
| `hr.abyz-lab.work` | **실제 사이트** — 직원들이 쓰는 곳 |
| `숫자.hr-portal.pages.dev` | **미리보기** — 나만 확인하는 임시 화면 |

미리보기는 PR이 정리되면 자동으로 사라진다.

# 6장. 승인 요청과 반영

## 6-1. 검토 요청하기

PR 화면 오른쪽에 **`Reviewers`** 항목이 있다. 톱니바퀴를 눌러 담당자를 선택한다.

담당자에게 알림이 간다.

## 6-2. 수정 요청을 받았을 때

담당자가 "여기를 이렇게 고쳐주세요" 라고 댓글을 달 수 있다.

그럴 때는 **PR을 새로 만들 필요가 없다.** 같은 브랜치에서 다시 고치면 자동으로 이 PR에 반영된다.

1. PR 화면 상단의 **`Files changed`** 탭 클릭
2. 고칠 파일의 오른쪽 `...` → `Edit file`
3. 고치고 `Commit changes`
4. 이번에는 **기존 브랜치에 저장**을 선택한다 (새 브랜치를 또 만들지 않는다)

## 6-3. 반영되기까지

담당자가 승인하고 **`Merge pull request`** 를 누르면 원본에 합쳐진다.

그다음은 자동이다.

```
병합됨
  → 자동 검사 최종 통과
  → 서버가 변경 내용을 가져감
  → 실제 사이트에 반영  (몇 분 이내)
```

**당신이 서버에 접속할 일은 없다.**

## 6-4. 반영 확인

몇 분 뒤 https://hr.abyz-lab.work 를 연다.

화면이 그대로라면 **`Ctrl + F5`** 를 누른다.
(그냥 F5는 브라우저가 기억하던 예전 화면을 보여줄 수 있다)

# 7장. 화면이 어떻게 만들어져 있는가

파일을 고치려면 구조를 알아야 한다. 최소한만 설명한다.

## 7-1. 파일 하나에 세 가지가 들어 있다

`public/index.html` 안에는 세 종류의 내용이 섞여 있다.

| 종류 | 하는 일 | 비유 |
|---|---|---|
| **CSS** (`<style>` 안) | 색깔, 크기, 배치 | 옷과 화장 |
| **HTML** (`<body>` 안) | 화면의 뼈대 | 뼈대 |
| **JavaScript** (`<script>` 안) | 클릭하면 일어나는 동작 | 근육과 신경 |

## 7-2. 메뉴는 여기서 정해진다

파일 안에서 `const NAV` 를 검색하면 이런 부분이 나온다.

```javascript
const NAV = [
  { id:'home',   label:'홈',        ... },
  { id:'attend', label:'근태·휴가',  ... },
  { id:'pay',    label:'급여·계약',  ... },
  ...
];
```

**왼쪽 사이드바 메뉴가 이 목록대로 만들어진다.**
`label` 뒤의 글자를 바꾸면 메뉴 이름이 바뀐다.

## 7-3. 각 화면은 함수가 만든다

`function` 으로 시작하는 부분들이 각각 하나의 화면을 담당한다.

```javascript
function leaveContent(){ ... }     // 연차 신청 화면
function payslipContent(){ ... }   // 급여명세서 화면
function orgChart(){ ... }         // 조직도 화면
```

**새 메뉴를 만들려면** ① 화면을 만드는 함수를 추가하고 ② `NAV` 목록에 항목을 넣으면 된다.
이 작업은 AI에게 요청하면 된다. 당신은 "어디를 고치는 것인지" 만 알면 된다.

## 7-4. `public` 폴더의 규칙

**`public` 폴더 안의 파일만 인터넷에 공개된다.**

바꿔 말하면, 여기에 넣은 파일은 **누구나 볼 수 있다.**

> ⚠️ 비밀번호가 적힌 파일, 내부 문서, 직원 명단 같은 것을 `public` 안에 넣으면 안 된다.

# 8장. 기능(모듈) 만들기

여기가 이 문서의 핵심이다. 기능 하나를 어떻게 만들어 나가는가.

## 8-1. 5단계 사이클

어떤 기능을 만들든 **항상 이 순서**를 반복한다.

```
① 정의  →  ② 설계  →  ③ 요청  →  ④ 확인  →  ⑤ 승인요청
```

---

### ① 정의 — 무엇을 만들지 한 문장으로 쓴다

**애매하면 반드시 엉뚱한 것이 만들어진다.**

| 나쁜 예 | 좋은 예 |
|---|---|
| 연차 기능 만들기 | 직원이 시작일·종료일·휴가종류·사유를 입력해 연차를 신청하면, 팀장에게 결재 요청이 가고, 승인되면 잔여 연차가 줄어든다 |

한 문장으로 못 쓰겠다면 아직 무엇을 만들지 정해지지 않은 것이다. 그 상태로 시작하면 안 된다.

---

### ② 설계 — 종이에 두 가지를 적는다

코딩이 아니다. **말로 적으면 된다.**

**(가) 화면에 무엇이 있는가**

```
입력칸: 시작일, 종료일, 휴가 종류(고르기), 사유
버튼:   신청하기
목록:   내가 신청한 내역 (기간 / 일수 / 종류 / 상태)
```

**(나) 어떤 정보를 저장하는가**

```
- 누가 신청했는지
- 언제부터 언제까지
- 휴가 종류
- 사유
- 상태 (대기 / 승인 / 반려)
- 누가 언제 승인했는지
```

**(다) 지켜야 할 규칙**

```
- 남은 연차보다 많이 신청하면 막는다
- 반차는 0.5일로 계산한다
- 지난 날짜는 신청할 수 없다
```

**규칙을 안 적으면 안 만들어진다.** 이 부분을 가장 꼼꼼히 적어야 한다.

---

### ③ 요청 — AI에게 그대로 전달한다

②에서 적은 것을 그대로 붙여 넣으면 된다. 좋은 요청은 이렇게 생겼다.

```
연차 신청 모듈을 만들어줘.

[화면]
- 입력: 시작일, 종료일, 휴가종류(연차/반차/반반차/병가), 사유
- 버튼: 신청하기
- 아래에 내 신청 내역 목록 (기간/일수/종류/상태)

[저장할 정보]
- 신청자, 시작일, 종료일, 휴가종류, 사유, 상태, 승인자, 승인시각

[규칙]
- 남은 연차보다 많이 신청하면 막을 것
- 반차는 0.5일로 계산
- 지난 날짜는 신청 불가

[참고]
- public/index.html 의 기존 코드 스타일과 디자인을 그대로 따라줘
- 기존 화면이 망가지지 않게 해줘
```

**요청할 때 지킬 것**

- **한 번에 기능 하나만** 요청한다. "연차랑 출장이랑 결재 다 만들어줘"는 반드시 실패한다
- **규칙을 빠뜨리지 않는다.** 안 적으면 안 만들어진다
- **"기존 스타일을 따라달라"고 명시한다.** 안 그러면 화면이 따로 논다
- 결과가 이상하면 **"이 부분이 이렇게 나왔는데 이렇게 되어야 한다"** 고 구체적으로 다시 말한다

---

### ④ 확인 — 직접 눌러본다

만들어졌다고 끝이 아니다. **반드시 미리보기 화면에서 직접 확인한다.**

- [ ] 정상적인 값을 넣으면 잘 되는가
- [ ] **이상한 값**을 넣으면 막히는가
- [ ] 기존 화면이 망가지지 않았는가
- [ ] 휴대폰 화면에서도 보이는가

**이상한 값 테스트가 가장 중요하다.** 실제 사고는 대부분 여기서 난다.

이런 것들을 넣어본다.

| 넣어볼 값 | 확인할 것 |
|---|---|
| 빈칸으로 두고 신청 | 막히는가 |
| 종료일을 시작일보다 앞으로 | 막히는가 |
| 지난 날짜 | 막히는가 |
| 아주 큰 숫자 (999999) | 막히는가 |
| 남은 연차보다 많은 일수 | 막히는가 |

---

### ⑤ 승인 요청 — PR로 올린다

3장에서 배운 순서 그대로다. 커밋 메시지에 무엇을 만들었는지 적는다.

```
연차 신청 모듈 추가 - 휴가 종류 선택 및 잔여 연차 검증
```

**기능 하나가 끝날 때마다 PR을 만든다.**
여러 개를 한꺼번에 올리면 문제가 생겼을 때 원인을 찾을 수 없다.

## 8-2. 어떤 순서로 만들 것인가

**쉽고 위험이 낮은 것부터** 만든다. 어려운 것부터 하면 반드시 중간에 막힌다.

### 1단계 — 연습용 (여기서 시작한다)

**공지사항** 부터 만든다. 이유가 있다.

- 개인정보가 없어서 실수해도 피해가 없다
- 만들기 · 보기 · 고치기 · 지우기 라는 가장 기본 동작을 모두 연습할 수 있다
- 이 네 가지가 나머지 모든 기능의 기본이 된다

- [ ] 공지사항 목록 보기
- [ ] 공지사항 작성
- [ ] 공지사항 수정 · 삭제
- [ ] 실제로 저장되게 하기

### 2단계 — 기반 (이게 없으면 다음이 불가능하다)

- [ ] 로그인
- [ ] 직원 정보 관리
- [ ] 역할 구분 (직원 / 팀장 / 인사담당 / 관리자)
- [ ] 역할에 따라 볼 수 있는 것 제한하기

> ⚠️ 여기서 서두르면 안 된다. 나중에 뒤집으면 만든 것을 **전부 다시** 만들어야 한다.

### 3단계 — 결재 (많은 기능이 여기에 기댄다)

- [ ] 결재 요청 / 승인 / 반려
- [ ] 결재함
- [ ] 결재선 설정

### 4단계 — 근태 · 휴가

- [ ] 출퇴근 기록
- [ ] 연차 신청
- [ ] 남은 연차 자동 계산
- [ ] 초과근무 신청

### 5단계 — 출장 · 경비

- [ ] 출장 신청
- [ ] 경비 계산
- [ ] 정산

### 6단계 — 민감한 정보 (가장 마지막)

- [ ] 급여명세서
- [ ] 전자연봉계약서
- [ ] 평가

> **왜 급여가 마지막인가?**
> 가장 민감하기 때문이다. 앞 단계에서 로그인과 권한 관리가 충분히 검증된 다음에 손대야 한다.
> 급여 정보가 잘못 노출되는 사고는 되돌릴 방법이 없다.

### 7단계 — 우리 회사에 특히 필요한 것

- [ ] 교육 · 훈련 이력 관리

> 우리 회사는 의료기기를 만들기 때문에, 직원 교육 기록 관리가 **품질 심사에서 요구되는 항목**이다.
> 인사 시스템에 없으면 결국 엑셀로 따로 관리하게 되고, 심사 때 기록을 못 찾는 문제가 생긴다.

## 8-3. 진행 상황 보기

`README.md` 에 전체 할 일이 체크박스로 정리되어 있다.
하나를 끝낼 때마다 `- [ ]` 를 `- [x]` 로 바꾸면 진행률이 한눈에 보인다.

# 9장. 막혔을 때

## 9-1. 상황별 대처

| 상황 | 어떻게 할까 |
|---|---|
| 저장소가 404로 안 열린다 | 초대를 수락했는지, 맞는 계정으로 로그인했는지 확인 |
| 인증 앱의 숫자가 안 맞다고 나온다 | 숫자가 30초마다 바뀐다. 새 숫자가 나오면 바로 입력한다 |
| 휴대폰을 바꿔서 인증 앱이 없어졌다 | 저장해 둔 **복구 코드**를 사용한다. 없으면 관리자에게 알린다 |
| 빨간 X가 떴다 | `Details` 클릭 → 빨간 글씨 복사 → AI나 담당자에게 보여준다 |
| 미리보기가 안 만들어진다 | 5분 기다려 본다. 그래도 없으면 담당자에게 문의 |
| 실제 사이트에 반영이 안 된다 | `Ctrl + F5` 로 새로고침. 그래도 안 되면 5~10분 기다린다 |
| 뭔가 크게 잘못한 것 같다 | **PR을 `Close` 한다.** 아무것도 반영되지 않는다 |
| 이미 병합해 버렸는데 문제가 있다 | 담당자에게 알린다. 되돌릴 수 있다 |

## 9-2. 도움을 요청하는 요령

이렇게 물어보면 빨리 해결된다.

```
[무엇을 하려고 했는지]
연차 신청 화면에 휴가 종류 선택을 추가하려고 했습니다.

[어떻게 했는지]
public/index.html 의 leaveContent 함수를 고쳤습니다.

[무슨 일이 일어났는지]
```

# 10장. 지켜야 할 것

## 절대 하지 말 것

| 하지 말 것 | 이유 |
|---|---|
| **실제 직원의 개인정보 입력** | 지금은 로그인이 없다. 실명·연락처·급여를 넣으면 안 된다 |
| **비밀번호나 인증키를 파일에 적기** | 한 번 올라가면 지워도 기록에 영구히 남는다 |
| **`main` 브랜치에 직접 저장** | 확인 없이 실제 사이트에 반영된다 |
| **`docker-compose.yml` 수정** | 서버 설정 파일이다. 잘못 고치면 사이트가 멈춘다 |
| **`public` 폴더에 비공개 자료 넣기** | 인터넷에 그대로 공개된다 |
| **한 PR에 여러 기능 몰아넣기** | 문제가 생겼을 때 원인을 못 찾는다 |

## 항상 할 것

- 커밋 메시지에 **무엇을 왜 바꿨는지** 적기
- 기능 하나 끝날 때마다 PR 만들기
- 미리보기로 **눈으로 확인**하기
- 이상한 값 넣어보기
- **모르면 물어보기** — 추측으로 진행하지 않는다

# 부록 A. 작업 순서 요약

늘 이 순서다. 이것만 외우면 된다.

```
1. GitHub 저장소 열기
2. 고칠 파일 클릭 → 연필 아이콘 ✏️
3. 내용 수정
4. Commit changes...
5. 메시지 적기 + "Create a new branch" 선택 ← 중요
6. Propose changes → Create pull request
7. 검사 결과 기다리기 (초록 체크 확인)
8. 미리보기 주소로 눈으로 확인
9. 담당자에게 검토 요청
10. 승인되면 자동으로 사이트에 반영됨
```

# 부록 B. 용어 사전

| 용어 | 뜻 |
|---|---|
| GitHub | 파일과 변경 기록을 보관하는 공용 문서함 |
| 저장소 (Repository) | 프로젝트 하나가 담긴 폴더 |
| 브랜치 (Branch) | 원본을 건드리지 않고 따로 작업하는 사본 |
| main | 원본 브랜치. 실제 사이트의 기준이 되는 것 |
| 커밋 (Commit) | 고친 내용을 저장하는 것 |
| PR (Pull Request) | "확인해 주세요" 요청서 |
| 리뷰 (Review) | 다른 사람이 확인하는 것 |
| 병합 (Merge) | 승인된 내용을 원본에 합치는 것 |
| CI / 자동 검사 | 사람이 보기 전에 기계가 먼저 확인하는 단계 |
| 미리보기 (Preview) | 반영 전에 결과를 볼 수 있는 임시 화면 |
| 배포 (Deploy) | 만든 것을 실제 사이트에 올리는 일 |
| HTML | 화면의 뼈대 |
| CSS | 화면의 모양 (색, 크기, 배치) |
| JavaScript | 화면의 동작 (클릭, 계산) |
| 모듈 | 기능 하나의 단위 (예: 연차 신청) |
| 프론트엔드 | 사용자가 보는 화면 부분 |
| 백엔드 | 화면 뒤에서 정보를 처리하는 부분 |
| 데이터베이스 | 정보를 저장해 두는 곳 |
