# 초심자 가이드 — 인사 통합포털 만들기

이 문서는 **개발 경험이 전혀 없는 분**을 위한 것이다.
서버에 접속하는 방법부터 시작해서, 기능(모듈)을 하나씩 만들어 나가는 순서까지 순차적으로 설명한다.

읽는 순서대로 따라 하면 된다. 건너뛰지 않는 것을 권한다.

---

## 이 문서를 읽기 전에

### 미리 알아둘 것

**혼자 코드를 다 작성하지 않아도 된다.** 이 가이드는 AI 코딩 도구(Claude Code 등)와 함께 작업하는 것을 전제로 한다.
당신이 할 일은 다음 네 가지다.

1. **무엇을 만들지 결정한다** — 이건 사람만 할 수 있다
2. **AI에게 정확히 요청한다** — 이 가이드가 방법을 알려준다
3. **결과를 확인한다** — 화면을 열어보고 의도대로인지 본다
4. **기록을 남긴다** — 커밋하고 저장한다

코드를 한 줄도 직접 못 써도 진행할 수 있다. 다만 **무엇이 어떻게 돌아가는지는 이해해야 한다.** 그래야 잘못된 결과를 알아챈다.

### 준비물

# 1장. 큰 그림 이해하기

코드를 만지기 전에 지금 무엇이 어떻게 연결되어 있는지부터 안다.

## 1-1. 웹사이트는 어떻게 보이는가

당신이 브라우저에서 주소를 입력하면, 그 주소에 해당하는 **컴퓨터**가 파일을 보내준다. 그 컴퓨터를 **서버**라고 부른다.

```
당신의 브라우저  →  "hr.abyz-lab.work 페이지 주세요"  →  서버
당신의 브라우저  ←  index.html 파일 전송            ←  서버
```

우리 서버는 사무실에 있는 **Dell OptiPlex 3060 PC** 한 대다. 특별한 장비가 아니라 그냥 리눅스가 설치된 컴퓨터다.

## 1-2. 우리 시스템의 구성

```
① 인터넷의 사용자
        ↓
② Cloudflare  (전 세계에 있는 중계 회사)
        ↓
③ 터널        (서버와 Cloudflare를 잇는 안전한 통로)
        ↓
④ 도커 컨테이너 (서버 안에서 웹서버 역할을 하는 상자)
        ↓
⑤ public/index.html  (실제 화면 파일)
```

각각을 비유하면 이렇다.

| 구성 요소 | 비유 | 역할 |
|---|---|---|
| **서버** | 창고 | 파일을 보관하고 요청에 응답한다 |
| **도커 컨테이너** | 창고 안의 규격 상자 | 프로그램을 다른 것과 섞이지 않게 격리해서 돌린다 |
| **Cloudflare 터널** | 창고에서 밖으로 나가는 전용 통로 | 창고 문(포트)을 열지 않고도 외부에서 접근하게 해준다 |
| **Git / GitHub** | 문서 버전 관리 캐비닛 | 누가 언제 무엇을 바꿨는지 전부 기록하고, 되돌릴 수 있게 한다 |

## 1-3. 왜 터널을 쓰는가

보통 외부에서 서버에 접근하려면 **방화벽에 구멍을 뚫어야** 한다. 그러면 그 구멍으로 공격도 들어온다.

터널은 반대다. **서버가 먼저 Cloudflare로 나가서** 연결을 만들어 둔다. 외부에서 들어오는 문은 하나도 열지 않는다. 훨씬 안전하다.

## 1-4. 지금 상태

**아직 진짜 시스템이 아니다.** 화면만 있는 모형이다.

- 화면에 보이는 "홍길동", "급여 3,215,400원"은 전부 **가짜 데이터**이고 파일에 그냥 적혀 있다
- 로그인이 없다
- "신청하기" 버튼을 눌러도 아무 일도 일어나지 않는다
- 데이터를 저장하는 곳(데이터베이스)이 없다

앞으로 할 일은 이 모형을 **진짜로 동작하는 시스템**으로 바꾸는 것이다.

# 2장. 서버에 접속하기

## 2-1. 터미널이란

**터미널**은 컴퓨터에게 글자로 명령을 내리는 창이다. 마우스 대신 키보드로 조작한다고 생각하면 된다.

처음엔 어렵게 느껴지지만, 실제로 쓰는 명령은 10개 남짓이다.

## 2-2. 터미널 열기 (Windows)

1. 키보드에서 **Windows 키**를 누른다
2. `터미널` 이라고 입력한다
3. **터미널** 앱을 클릭한다

검은 창이 뜨고 이런 글자가 보인다.

```
PS C:\Users\admin>
```

이것을 **프롬프트**라고 한다. "명령을 입력하세요"라는 뜻이다. `PS C:\Users\admin>` 부분은 안내 문구이고, 당신은 그 **뒤에** 명령을 입력한다.

> 이 문서에서 명령어를 보여줄 때는 프롬프트를 빼고 명령만 적는다. 그대로 복사해서 붙여넣으면 된다.

## 2-3. 서버에 접속하기

터미널에 아래를 입력하고 **Enter**를 누른다.

```
ssh abyz-lab0@100.73.145.44
```

- `ssh` — 다른 컴퓨터에 안전하게 접속하는 명령
- `abyz-lab0` — 서버에서 쓸 계정 이름
- `100.73.145.44` — 서버의 주소 (Tailscale 내부 주소)

비밀번호를 물어보면 입력하고 Enter를 누른다.

> **주의:** 비밀번호를 입력해도 화면에 아무것도 안 보인다. `****` 같은 표시도 없다. **고장이 아니다.** 보안상 일부러 그렇게 되어 있다. 그냥 입력하고 Enter를 누르면 된다.

접속에 성공하면 프롬프트가 이렇게 바뀐다.

```
abyz-lab0@abyz-lab0-OptiPlex-3060:~$
```

**이제부터 입력하는 명령은 내 PC가 아니라 서버에서 실행된다.** 이 구분이 매우 중요하다.

| 프롬프트 모양 | 어디에 있는가 |
|---|---|
| `PS C:\Users\admin>` | 내 Windows PC |
| `abyz-lab0@abyz-lab0-OptiPlex-3060:~$` | 서버 |

## 2-4. 접속 끊기

```
exit
```

프롬프트가 다시 `PS C:\Users\admin>` 로 돌아오면 서버에서 나온 것이다.

## 2-5. 접속이 안 될 때

| 증상 | 원인과 해결 |
|---|---|
| `Connection timed out` | Tailscale이 꺼져 있다. 작업표시줄 아이콘 확인 후 연결 |
| `Permission denied` | 비밀번호가 틀렸다. 다시 시도 |
| `Could not resolve hostname` | 주소를 잘못 입력했다. 오타 확인 |

# 3장. 리눅스 기본 명령 10개

서버는 리눅스다. 아래 10개만 알면 이 프로젝트에서 하는 일은 거의 다 된다.

## 3-1. 지금 어디에 있는지 보기 — `pwd`

```
pwd
```

결과:
```
/home/abyz-lab0
```

**폴더 위치**를 알려준다. 길을 잃으면 이걸 먼저 친다.

## 3-2. 무엇이 있는지 보기 — `ls`

```
ls
```

현재 폴더 안의 파일과 폴더 목록이 나온다. 자세히 보려면:

```
ls -la
```

- `-l` — 자세히 (크기, 날짜, 권한)
- `-a` — 숨김 파일까지 전부

## 3-3. 폴더 이동 — `cd`

```
cd workspace
```

`workspace` 폴더 안으로 들어간다.

```
cd ..
```

한 단계 위로 나온다. (`..`은 "상위 폴더"라는 뜻)

```
cd ~
```

홈 폴더로 돌아간다. (`~`는 "내 홈 폴더")

**우리 프로젝트 폴더로 가는 명령**은 이것이다. 자주 쓰게 되니 기억해 두자.

```
cd ~/workspace/github-hnabyz-bot/hr-portal
```

## 3-4. 파일 내용 보기 — `cat`

```
cat README.md
```

파일 내용을 화면에 전부 출력한다. 파일이 길면 화면이 넘어가니, 그럴 땐:

```
less README.md
```

위아래 화살표로 스크롤하고, **`q`** 를 누르면 나온다.

## 3-5. 파일 편집 — `nano`

```
nano README.md
```

편집기가 열린다. 화살표로 이동하며 글자를 고칠 수 있다.

| 키 | 동작 |
|---|---|
| `Ctrl + O` → `Enter` | 저장 |
| `Ctrl + X` | 나가기 |
| `Ctrl + K` | 현재 줄 삭제 |

> 화면 아래에 `^O Write Out` 처럼 표시된 것에서 `^` 는 **Ctrl 키**를 뜻한다.

## 3-6. 나머지 5개

| 명령 | 하는 일 | 예시 |
|---|---|---|
| `mkdir` | 폴더 만들기 | `mkdir docs` |
| `cp` | 파일 복사 | `cp a.txt b.txt` |
| `mv` | 이동 / 이름 변경 | `mv a.txt b.txt` |
| `rm` | 삭제 **(되돌릴 수 없음)** | `rm a.txt` |
| `curl -I` | 웹주소가 살아있는지 확인 | `curl -I https://hr.abyz-lab.work` |

> **`rm` 은 조심해서 쓴다.** 휴지통이 없다. 지우면 끝이다. 특히 `rm -rf` 는 폴더째 통째로 지우는 명령이라, 확신이 없으면 쓰지 않는다.

## 3-7. 시간을 아끼는 요령

- **Tab 키** — 파일명을 몇 글자 치고 Tab을 누르면 나머지가 자동 완성된다. 오타를 크게 줄여준다
- **위쪽 화살표** — 직전에 쓴 명령이 다시 나온다
- **Ctrl + C** — 명령이 멈추지 않을 때 강제 중단

# 4장. Git과 GitHub

## 4-1. 왜 필요한가

파일을 수정하다 보면 반드시 이런 일이 생긴다.

- 고쳤는데 더 나빠졌다. 원래대로 되돌리고 싶다
- 어제까지는 됐는데 오늘 안 된다. 뭘 바꿨는지 모르겠다
- 다른 사람이 뭘 고쳤는지 알고 싶다

**Git**이 이걸 해결한다. 파일이 바뀔 때마다 사진을 찍어두고, 언제든 그 시점으로 돌아갈 수 있게 해준다.

**GitHub**은 그 기록을 인터넷에 보관해주는 서비스다. 서버가 고장 나도 코드는 남는다.

## 4-2. 세 가지 개념

| 용어 | 뜻 |
|---|---|
| **커밋(commit)** | 지금 상태를 사진 찍어 저장하는 것 |
| **푸시(push)** | 그 사진을 GitHub에 올리는 것 |
| **풀(pull)** | GitHub에 있는 최신 내용을 서버로 내려받는 것 |

## 4-3. 기본 흐름

파일을 고친 뒤에는 **항상** 이 순서를 따른다.

**① 프로젝트 폴더로 이동**

```
cd ~/workspace/github-hnabyz-bot/hr-portal
```

**② 무엇이 바뀌었는지 확인**

```
git status
```

바뀐 파일이 빨간색으로 나온다.

**③ 저장할 파일 선택**

```
git add .
```

`.` 은 "바뀐 것 전부"라는 뜻이다.

**④ 사진 찍기 (커밋)**

```
git commit -m "연차 신청 화면에 휴가 종류 선택 추가"
```

`-m` 뒤 따옴표 안에 **무엇을 왜 바꿨는지** 적는다. 나중에 이 문장만 보고 찾게 되므로, "수정", "ㅇㅇ" 같은 건 쓰지 않는다.

**⑤ GitHub에 올리기**

```
git push
```

## 4-4. 되돌리기

아직 커밋하지 않았고, 방금 고친 게 마음에 안 들면:

```
git checkout .
```

마지막 커밋 상태로 전부 되돌아간다. **저장하지 않은 수정은 사라지니** 주의한다.

## 4-5. 실습 — 첫 커밋 해보기

실제로 한 번 해본다. 실수해도 문제없는 안전한 연습이다.

```
cd ~/workspace/github-hnabyz-bot/hr-portal
```

```
nano README.md
```

맨 아래로 내려가서 아무 줄이나 하나 추가한다. 예: `연습용 줄입니다.`
`Ctrl+O` → `Enter` → `Ctrl+X` 로 저장하고 나온다.

```
git status
```

`modified: README.md` 가 보이면 성공이다.

```
git add .
```

```
git commit -m "Git 사용법 연습"
```

```
git push
```

브라우저에서 https://github.com/hnabyz-bot/hr-portal 을 열어보면 방금 추가한 줄이 보인다.

연습이 끝났으면 그 줄을 다시 지우고 같은 순서로 커밋한다.

# 5장. 프로젝트 구조 이해하기

## 5-1. 파일 배치

```
hr-portal/
├── README.md              ← 프로젝트 설명서와 할 일 목록
├── docs/
│   └── beginner-guide.md  ← 지금 읽고 있는 문서
├── docker-compose.yml     ← 웹서버를 어떻게 띄울지 적은 설정
└── public/
    └── index.html         ← 실제 화면 (전부 여기 들어 있다)
```

## 5-2. `public/` 폴더가 특별한 이유

**`public/` 안의 파일만 인터넷에 공개된다.**

이건 매우 중요한 규칙이다. 만약 프로젝트 폴더 전체를 공개했다면, `.git` 폴더(모든 변경 이력과 소스)까지 누구나 내려받을 수 있게 된다.

**규칙: 외부에 보여도 되는 파일만 `public/` 에 넣는다.**

설정 파일, 비밀번호, 내부 문서는 절대 `public/` 밖에 둔다.

## 5-3. `index.html` 이 하는 일

이 파일 하나에 화면 전체가 들어 있다. 572줄이고, 세 부분으로 나뉜다.

| 부분 | 위치 | 역할 |
|---|---|---|
| **CSS** (모양) | 위쪽 `<style>` 안 | 색깔, 크기, 배치 |
| **HTML** (뼈대) | 가운데 `<body>` 안 | 화면의 큰 틀 |
| **JavaScript** (동작) | 아래쪽 `<script>` 안 | 메뉴 클릭, 화면 전환, 계산 |

### 화면 내용이 어디에 있는가

`<script>` 안의 함수들이 각 화면을 만든다.

```javascript
function leaveContent(){ ... }      // 연차 신청 화면
function payslipContent(){ ... }    // 급여명세서 화면
function orgChart(){ ... }          // 조직도 화면
```

### 메뉴 구성은 어디에 있는가

`NAV` 라는 목록이 왼쪽 사이드바와 상단 탭을 결정한다.

```javascript
const NAV = [
  { id:'home', label:'홈', ... },
  { id:'attend', label:'근태·휴가', ... },
  ...
];
```

**메뉴를 추가하려면 이 목록에 항목을 추가하고, 그 화면을 그리는 함수를 만들면 된다.** 새 모듈을 만들 때 반복하게 될 작업이다.

이미 열려 있었다면 **`Ctrl + F5`** 를 눌러 새로고침한다. (그냥 F5는 예전 화면이 남을 수 있다)

왼쪽 위 글자가 바뀌었으면 성공이다.

> **왜 바로 반영되는가?**
> 도커 컨테이너가 `public/` 폴더를 직접 바라보고 있기 때문이다. 파일을 고치면 즉시 반영된다. 재시작이 필요 없다.

## 6-5. 되돌리기

연습이었으므로 원래대로 돌린다.

```

```

브라우저에서 `Ctrl + F5` 로 다시 확인하면 원래 글자로 돌아와 있다.

**여기까지 됐다면 기본은 끝났다.** 파일을 고치고, 확인하고, 되돌릴 수 있게 된 것이다.

# 8장. 왜 지금 구조로는 부족한가

앞으로 무엇을 만들어야 하는지 이해하려면, 지금 무엇이 없는지부터 알아야 한다.

## 8-1. 정적 vs 동적

지금 우리 사이트는 **정적**이다. 누가 접속하든 **똑같은 파일**을 보여준다.

```
사용자 A → index.html (홍길동 정보)
사용자 B → index.html (홍길동 정보)   ← 똑같다
```

진짜 인사 시스템은 **동적**이어야 한다. 접속한 사람에 따라 다른 내용을 보여줘야 한다.

```
홍길동 로그인 → 홍길동의 연차 15.5일
김영희 로그인 → 김영희의 연차 8일
```

## 8-2. 그러려면 세 가지가 필요하다

| 필요한 것 | 하는 일 | 비유 |
|---|---|---|
| **데이터베이스** | 직원 정보, 연차 기록, 급여를 보관 | 서류 캐비닛 |
| **백엔드(서버 프로그램)** | 누가 요청했는지 확인하고 맞는 데이터를 꺼내줌 | 캐비닛을 관리하는 담당자 |
| **로그인(인증)** | 접속한 사람이 누구인지 확인 | 출입증 확인 |

## 8-3. 가장 중요한 원칙

> **화면에서 메뉴를 숨기는 것은 보안이 아니다.**

예를 들어 "급여 메뉴는 인사팀에게만 보이게" 만들었다고 하자. 하지만 화면에서 안 보일 뿐, 데이터를 요청하는 주소를 직접 입력하면 그냥 나온다.

**권한 확인은 반드시 백엔드에서 해야 한다.** 이건 인사 시스템에서 특히 중요하다. 남의 급여가 보이는 사고는 되돌릴 수 없다.

# 9장. 모듈 개발 순서

여기가 이 문서의 핵심이다. **기능 하나(=모듈)를 어떻게 만들어 나가는가.**

## 9-1. 모듈 개발 5단계 사이클

어떤 모듈을 만들든 **항상 이 5단계**를 반복한다.

```
① 정의  →  ② 설계  →  ③ 구현  →  ④ 확인  →  ⑤ 기록
```

### ① 정의 — 무엇을 만들지 한 문장으로 쓴다

애매하면 반드시 잘못 만들어진다. 구체적으로 쓴다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 연차 기능 만들기 | 직원이 시작일·종료일·휴가종류·사유를 입력해 연차를 신청하면, 팀장에게 결재 요청이 가고, 승인되면 잔여 연차가 차감된다 |

### ② 설계 — 화면과 데이터를 종이에 적는다

두 가지만 정리하면 된다.

**화면에 무엇이 있는가**
- 입력칸: 시작일, 종료일, 휴가 종류(선택), 사유
- 버튼: 신청하기
- 목록: 내 신청 내역 (기간 / 일수 / 종류 / 상태)

**어떤 정보를 저장하는가**
- 누가 신청했는지
- 언제부터 언제까지
- 휴가 종류
- 사유
- 현재 상태 (대기 / 승인 / 반려)
- 승인한 사람, 승인한 시각

### ③ 구현 — AI에게 요청한다

②에서 정리한 내용을 그대로 전달한다. 좋은 요청은 이렇게 생겼다.

```
연차 신청 모듈을 만들어줘.

[화면]
- 입력: 시작일, 종료일, 휴가종류(연차/반차/반반차/병가), 사유
- 버튼: 신청하기
- 아래에 내 신청 내역 목록 (기간/일수/종류/상태)

[저장할 정보]
- 신청자, 시작일, 종료일, 휴가종류, 사유, 상태, 승인자, 승인시각

[규칙]
- 잔여 연차보다 많이 신청하면 막아야 함
- 반차는 0.5일로 계산
- 과거 날짜는 신청 불가

기존 index.html의 코드 스타일과 디자인을 그대로 따라줘.
```

**요청할 때 지켜야 할 것**
- 한 번에 **한 모듈**만 요청한다. "연차랑 출장이랑 결재 다 만들어줘"는 실패한다
- 규칙(제약조건)을 빠뜨리지 않는다. 안 적으면 안 만들어진다
- "기존 스타일을 따라달라"고 명시한다. 그래야 화면이 따로 놀지 않는다

### ④ 확인 — 직접 눌러본다

만들어졌다고 끝이 아니다. **반드시 직접 확인한다.**

- [ ] 정상적인 값을 넣으면 잘 되는가
- [ ] **이상한 값**을 넣으면 막히는가 (음수, 빈칸, 과거 날짜, 아주 큰 숫자)
- [ ] 화면이 기존 디자인과 어울리는가
- [ ] 휴대폰 화면에서도 보이는가

특히 **이상한 값 테스트**를 빠뜨리면 안 된다. 실제 사고는 대부분 여기서 난다.

### ⑤ 기록 — 커밋하고 올린다

```
git add .
```

```
git commit -m "연차 신청 모듈 추가 - 휴가 종류 선택 및 잔여 연차 검증"
```

```
git push
```

**모듈 하나가 끝날 때마다** 커밋한다. 여러 개를 한꺼번에 커밋하면 문제가 생겼을 때 어디가 원인인지 못 찾는다.

## 9-2. 어떤 순서로 만들 것인가

**쉽고 위험이 낮은 것부터** 만든다. 어려운 것부터 하면 중간에 막힌다.

### 1단계 — 연습용 모듈 (여기서 시작)

**공지사항**부터 만든다. 이유가 있다.

- 개인정보가 없어서 실수해도 피해가 없다
- 만들기·읽기·수정하기·지우기 라는 가장 기본 동작을 전부 연습할 수 있다
- 이 네 가지가 나머지 모든 모듈의 기본이 된다

- [ ] 공지사항 목록 보기
- [ ] 공지사항 작성
- [ ] 공지사항 수정·삭제
- [ ] 데이터베이스에 실제로 저장하기

### 2단계 — 기반 (여기가 없으면 다음이 불가능하다)

- [ ] 로그인 기능
- [ ] 직원 정보 관리 (인사 마스터)
- [ ] 역할 구분 — 임직원 / 팀장 / 인사담당 / 관리자
- [ ] **역할에 따른 접근 제어 (백엔드에서 확인)**

> 여기서 서두르면 안 된다. 나중에 뒤집으면 만든 것을 전부 다시 만들어야 한다.

### 3단계 — 결재 (많은 기능이 여기에 의존한다)

- [ ] 결재 요청 / 승인 / 반려
- [ ] 결재함 (내가 처리할 것 / 내가 올린 것)
- [ ] 결재선 설정

### 4단계 — 근태·휴가

- [ ] 출퇴근 기록
- [ ] 연차 신청 (결재 연동)
- [ ] 연차 잔여 자동 계산
- [ ] 초과근무 신청 및 실적 등록

### 5단계 — 출장·경비

- [ ] 출장 신청
- [ ] 경비 산출 (규정 한도 검증 포함)
- [ ] 정산

### 6단계 — 민감 정보 (가장 마지막)

- [ ] 급여명세서 조회
- [ ] 전자연봉계약서
- [ ] 평가

> **왜 급여가 마지막인가?**
> 가장 민감하기 때문이다. 앞 단계에서 로그인·권한·기록 남기기가 충분히 검증된 뒤에 손대야 한다. 급여 정보가 잘못 노출되는 사고는 복구할 방법이 없다.

### 7단계 — 회사 특성상 필요한 것

- [ ] **교육·훈련 이력 관리**

> 우리 회사는 의료기기를 만들기 때문에, 직원 교육 기록을 관리하는 것이 **품질 심사에서 요구되는 항목**이다. (ISO 13485 / KGMP)
> 인사 시스템에 없으면 결국 엑셀로 따로 관리하게 되고, 심사 때 기록을 못 찾는 문제가 생긴다.

# 10장. 문제가 생겼을 때

## 10-1. 사이트가 안 열린다

**위에서부터 순서대로** 확인한다.

**① 컨테이너가 돌고 있는가**

```
cd ~/workspace/github-hnabyz-bot/hr-portal && docker compose ps
```

`Up` 이 아니면:
```
docker compose up -d
```

**② 서버 안에서는 열리는가**

```
curl -I http://127.0.0.1:8080/
```

`200 OK` 가 나오면 컨테이너는 정상이다. 문제는 터널에 있다.

**③ 터널이 돌고 있는가**

```
sudo systemctl status cloudflared
```

`active (running)` 이 아니면:
```
sudo systemctl restart cloudflared
```

**④ 밖에서 열리는가**

```
curl -I https://hr.abyz-lab.work
```

## 10-2. 화면이 안 바뀐다

브라우저가 예전 화면을 기억하고 있는 경우가 대부분이다.

- **`Ctrl + F5`** 로 강제 새로고침
- 그래도 안 되면 브라우저 시크릿 창에서 열어본다

## 10-3. 무언가 크게 망가졌다

당황하지 않아도 된다. Git이 있으면 되돌릴 수 있다.

**아직 커밋하지 않은 수정을 전부 취소**
```
git checkout .
```

**최근 기록 확인**
```
git log --oneline -10
```

## 10-4. 기록(로그) 보는 법

문제의 원인은 대부분 로그에 적혀 있다.

```
docker compose logs --tail 50
```

```
sudo journalctl -u cloudflared -n 50
```

**AI에게 도움을 요청할 때는 이 출력을 그대로 복사해서 보여준다.** "안 돼요"보다 훨씬 빨리 해결된다.

# 11장. 지켜야 할 안전 수칙

## 절대 하지 말 것

- **실제 직원의 개인정보를 넣지 않는다** — 지금은 인증이 없는 상태다. 실명, 실제 연락처, 실제 급여를 넣으면 안 된다
- **비밀번호나 접속키를 코드에 적지 않는다** — GitHub에 올라가면 되돌릴 수 없다. 삭제해도 기록에 남는다
- **`public/` 밖의 파일을 `public/` 안으로 옮기지 않는다** — 인터넷에 공개된다
- **확신 없이 `rm -rf` 를 쓰지 않는다** — 되돌릴 수 없다
- **`sudo` 가 붙은 명령은 이해한 뒤에만 실행한다** — 시스템 전체를 바꿀 수 있는 권한이다

## 항상 할 것

- **작업 전 `git status` 로 현재 상태 확인**
- **모듈 하나 끝날 때마다 커밋**
- **커밋 메시지에 무엇을 왜 바꿨는지 기록**
- **이상한 값을 넣어보는 테스트**
- **모르면 물어본다** — 추측으로 실행하지 않는다
