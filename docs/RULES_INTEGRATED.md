목적
비개발자(또는 개발 초심자)가 공동으로 작업할 때 반복되는 실수와 위험한 관행을 방지하기 위한 레포 규칙과 체크리스트를 정리합니다. 이 이슈를 레퍼런스로 삼아 PR/브랜치/시크릿/배포 관련 실수를 줄이고, 새로운 기여자가 따라하기 쉽도록 합니다.

통합 로그: #12–#16 규칙 관련 항목을 본 이슈로 통합했습니다.

제안 규칙(항목별 체크리스트)
- [ ] 브랜치 관리
  - 브랜치는 기능/버그 단위로 생성하세요. 네이밍 예: feature/short-description 또는 fix/short-description.
  - main이나 release 브랜치로 직접 푸시하지 마세요. 모든 변경은 PR을 통해 병합하세요.
  - 병합된 브랜치는 정리(삭제)하세요.

- [ ] PR 작성 및 리뷰
  - PR 제목과 본문에 무엇을 바꿨는지, 왜 바꿨는지, 배포 시 주의사항을 명확히 적으세요.
  - PR 체크리스트를 사용하세요(예: 로컬 동작 확인, 시크릿 미포함 확인, 한글 깨짐 확인 등).
  - 기능이 백엔드/시크릿을 요구하면 배포 전 필요한 절차(.env 생성, docker compose up 등)를 PR 본문에 반드시 포함하세요.

- [ ] 시크릿 및 민감 데이터
  - 절대 API 키/비밀번호/원문 규정 문서 등을 레포에 커밋하지 마세요. .env 또는 외부 비밀 저장소에 보관하세요.
  - .env.example 파일을 제공해 어떤 환경 변수가 필요한지 명시하세요.
  - 규정 원문(회사 내부 문서 등)은 저장소에 올리지 말고 서버의 별도 디렉터리(regulations/)에 두는 절차를 문서화하세요.

- [ ] 템플릿과 문서화
  - PR 템플릿과 이슈 템플릿을 만들어 PR/이슈 작성 표준을 강제하세요.
  - 배포·운영에 필요한 절차는 CONTRIBUTING.md 또는 DEPLOY.md에 정리하세요(예: 서버 .env 생성, docker compose 명령, 마이그레이션 절차).

- [ ] 배포/운영 안내
  - 백엔드가 새로 추가된 PR은 배포 전 담당자가 수행할 수 있는 체크리스트를 포함해야 합니다(예: 시크릿 등록, docker compose 최초 실행, 배포 스크립트 반영).

- [ ] CI/검증
  - 가능한 경우 GitHub Actions 등 CI를 통해 lint/test를 자동 실행하세요. PR 병합 조건에 CI 통과를 포함하세요.

우선 시행 제안
- main과 release 브랜치에 보호 규칙 적용(병합 전 리뷰 요구, 강제 CI 통과, 푸시 금지)
- 간단한 PR 템플릿 도입(제목/무엇을/왜/배포 참고사항/체크리스트)
- .env.example, CONTRIBUTING.md(초보자용 짧은 가이드) 추가

문의 및 피드백
이 이슈에 규칙을 추가하거나 수정해주세요. 실무 담당자 (운영, 보안, 개발자, Agent)가 책임자를 정해 항목을 확정하면 체크리스트를 팀 규정으로 고정하겠습니다.
